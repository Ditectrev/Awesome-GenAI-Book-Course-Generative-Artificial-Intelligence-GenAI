## Introduction to Generative AI (GenAI)

Generative Artificial Intelligence (GenAI) is how you get a model to produce text, images, audio, or a mix of those, then put that output into a product. This chapter gives you the working vocabulary: tokens, context windows, hosted APIs versus local checkpoints, and how training actually happens so you can choose a model on purpose. We then show how the rest of this book is organized as working loops, not a theory dump. The next chapter, Hosted Models, APIs, and Your First Working Loop, is where you create accounts, set spend caps, and make your first real call.

### What is Generative AI (GenAI)?

**Generative Artificial Intelligence (GenAI)** is software that samples new content from a probability distribution the model learned during training. You send instructions and context; the model predicts the next tokens (or pixels, or audio frames) until it stops. That is different from a search index, a rules engine, or a classifier that only picks a label. The job on a product team is not to "use AI." The job is to wrap a model in a loop you can test, budget, and ship: a prompt or tool call, a check on the output, and a path to the user.

You already meet GenAI as products: [ChatGPT](https://chatgpt.com/) from [OpenAI](https://openai.com/), [Claude](https://claude.ai/) from [Anthropic](https://www.anthropic.com/), [Gemini](https://gemini.google.com/) from Google, [Le Chat](https://chat.mistral.ai/) from [Mistral](https://mistral.ai/), and [DeepSeek](https://www.deepseek.com/). Those chats are useful, and they hide the bill, the context window, and the retry path. This book treats the same models as APIs and local runtimes you control.

- **Generation, not lookup.** The model can invent a plausible sentence that is not in any document you fed it. That is the feature and the failure mode. Later chapters cover retrieval, evaluation, and guardrails so you do not ship that invention as a fact.
- **A model is not a product.** A product has auth, spend caps, logging, fallbacks, and a UI. The model is one dependency, like a database, with worse latency and a meter on every request.
- **You will mix providers.** One team may call [OpenAI](https://openai.com/) for a default path, [Groq](https://groq.com/) for a cheap fast path, and [Ollama](https://ollama.com/) on a laptop for offline work. The next chapter starts that working loop.

#### Tokens, context windows, and why they matter on the job

A **token** is a chunk of text (or other input) the model actually sees. English often lands around four characters per token; code, URLs, and non-English text usually cost more. You are billed and limited in tokens, not words. Count them with the provider's tokenizer, not with `len(text)`. [OpenAI](https://openai.com/) publishes [tiktoken](https://github.com/openai/tiktoken) and a [tokenizer tool](https://platform.openai.com/tokenizer); [Anthropic](https://www.anthropic.com/) documents token counting in the [Claude API](https://docs.anthropic.com/en/docs/build-with-claude/token-counting); [Google Gemini](https://ai.google.dev/gemini-api/docs) exposes count methods on the [Gemini API](https://ai.google.dev/gemini-api/docs). If you skip this, you will blow the window, truncate the wrong end of a prompt, or get a surprise invoice.

The **context window** is the maximum tokens the model can attend to in one request: system instructions, retrieved chunks, tool results, chat history, and the reply you have not finished streaming yet. Windows now range from tens of thousands of tokens to a million-plus on some [Gemini](https://ai.google.dev/gemini-api/docs) and [Claude](https://docs.anthropic.com/en/docs/build-with-claude/context-windows) models. A bigger window is not free. Long prompts cost more, add latency, and still go stale. Treat the window as a budget:

- Put durable rules in a system prompt, not in every user turn.
- Put large documents behind retrieval later in Retrieval-Augmented Generation (RAG), instead of pasting the whole wiki.
- Measure prompt tokens and completion tokens separately. Completions are usually more expensive.
- When the window fills up, summarize or drop old turns on purpose. Do not let the client library silently drop the beginning of the prompt.

On the job, tokens show up as unit economics. If a support bot sends 8,000 tokens of history on every turn, you will feel it in the bill before you feel it in quality. The Shipping, Cost, and Operations chapter is where we cache, route, and cap that spend. Here you only need the reflex: **count tokens before you ship the prompt.**

#### Models, products, and open-weight checkpoints

Three names get mixed together. Keep them separate so you know what you are buying.

- **A model** is the trained network and its tokenizer. Examples: GPT-class models on the [OpenAI Platform](https://platform.openai.com/), Claude models on the [Anthropic Console](https://console.anthropic.com/), Gemini models on the [Gemini API](https://ai.google.dev/gemini-api/docs), Mistral models on [Mistral AI](https://mistral.ai/), DeepSeek models on the [DeepSeek API](https://api-docs.deepseek.com/).
- **A product** is the chat app or workspace wrapped around a model: [ChatGPT](https://chatgpt.com/), [Claude](https://claude.ai/), [Gemini](https://gemini.google.com/). Products add memory, browsing, file upload, and a ToS that is not the same as the API ToS. Do not assume a ChatGPT answer will behave like the API with the same model name.
- **An open-weight checkpoint** is a file of weights you can download, usually from the [Hugging Face Hub](https://huggingface.co/models), and run with [Ollama](https://ollama.com/), [llama.cpp](https://github.com/ggml-org/llama.cpp), [vLLM](https://github.com/vllm-project/vllm), or [Hugging Face Transformers](https://github.com/huggingface/transformers). Open weights are not automatically open source. The license on the [model card](https://huggingface.co/docs/hub/en/model-cards) decides whether you may use the weights commercially, and it does not give you the training data.

When you pick a default, write down all three: which model id, which product or API, and whether you can host the checkpoint yourself. "Use Llama" is not a decision. "Serve this Hub revision behind an OpenAI-compatible endpoint on our GPU box" is.

#### Text, image, audio, and multimodal generation in practice

Most of this book is text: chat completions, tool calls, JSON, and code. That is still the path you ship first, because it is the cheapest to test. The same providers now take mixed inputs.

- **Text.** Completions and chat APIs at [OpenAI](https://platform.openai.com/docs/guides/text), [Anthropic](https://docs.anthropic.com/en/docs/build-with-claude/text-generation), [Gemini](https://ai.google.dev/gemini-api/docs), [Mistral](https://docs.mistral.ai/), and [DeepSeek](https://api-docs.deepseek.com/). This is your default working loop.
- **Images.** Hosted image generation in [ChatGPT](https://chatgpt.com/) and the [OpenAI Images API](https://platform.openai.com/docs/guides/images), plus [Gemini image generation](https://ai.google.dev/gemini-api/docs/image-generation); local and open stacks such as [Diffusers](https://github.com/huggingface/diffusers), [ComfyUI](https://github.com/Comfy-Org/ComfyUI), and [AUTOMATIC1111 WebUI](https://github.com/AUTOMATIC1111/stable-diffusion-webui). [Flux](https://blackforestlabs.ai/)-class models sit between those worlds.
- **Audio.** Speech-to-text with [OpenAI Whisper](https://github.com/openai/whisper) or [whisper.cpp](https://github.com/ggml-org/whisper.cpp); realtime voice stacks later with [LiveKit Agents](https://github.com/livekit/agents).
- **Multimodal.** One request that includes a screenshot, a PDF page, or a photo plus a question. Vision in the same loop as text is often cheaper than dumping HTML into the prompt. We return to that in Images, Audio, and Other Modalities.

Do not start a product on five modalities. Start with text, add a screenshot path when the text path lies, and treat image or voice as a second loop with its own evals.

### How generative models are trained

You do not need to train a frontier model to ship GenAI. You do need to know what training did to the checkpoint you call, because that is why it hallucinates, refuses, or leaks a style. Training is a stack: machine learning, pretraining on datasets, then instruction tuning and preference data. Fine-tuning your own adapter is a later, expensive move we keep under Shipping, Cost, and Operations. Here we only explain the stack so you can read a model card without getting fooled.

#### Machine learning basics you need on the job

**Machine learning (ML)** means a program whose behavior comes from data and an optimization objective, not from a hand-written rule for every case. A generative model is a particularly large ML system: it maps a token sequence to a distribution over the next token. Three ideas are enough to work:

- **Train versus serve.** Training updates weights. Serving (inference) uses frozen weights to produce tokens. Your production path is almost always inference. If someone says "we should train," ask whether they mean a new pretrain, an instruction tune, a preference tune, or a small adapter. Those have different costs by orders of magnitude.
- **Loss and generalization.** The trainer minimizes a loss on examples it can see. The model will still fail on your tickets, your JSON schema, and your brand voice. That gap is why we evaluate with golden sets later, instead of trusting a demo.
- **Supervision.** Labels can be next-token text (pretraining), instruction-response pairs (instruction tuning), or rankings of two answers (preference training / RLHF). The quality of that supervision is the quality of the model.

If you already write software, treat training as a build pipeline you rarely run, and inference as the runtime you own. That split keeps you from turning every product bug into a fine-tune.

#### Pretraining, datasets, and data licenses

**Pretraining** is the expensive pass: next-token prediction on a huge mix of web pages, code, books, and other text (plus images or audio for multimodal models). The result is a base model that can complete text but is a poor assistant until it is instruction-tuned. You meet pretrained and post-trained checkpoints on the [Hugging Face Hub](https://huggingface.co/models) and behind hosted APIs.

Datasets are not a footnote. They decide what the model can talk about, what it memorizes, and what licenses attach to the weights.

- Read the **dataset** and **license** sections of the [Hugging Face model card](https://huggingface.co/docs/hub/en/model-cards) before you download a checkpoint. "Open weights" is not permission to use any output, and it is not a grant of the training corpus.
- Hosted APIs hide the corpus. You still have to read the provider's data-use and retention terms on [OpenAI](https://openai.com/policies/row-privacy-policy/), [Anthropic](https://www.anthropic.com/legal/privacy), [Google Gemini](https://ai.google.dev/gemini-api/terms), [Mistral](https://mistral.ai/terms/), and [DeepSeek](https://www.deepseek.com/). API data-use is often stricter than the consumer chat product, but only if you are actually on the API.
- Do not train or fine-tune on customer tickets, production logs, or third-party content unless you have a written right to do that. Shipping, Cost, and Operations covers data you must not train on. If you are unsure, retrieval beats training.

When a vendor says a model is "trained on the internet," translate that to: it will be fluent, it will be dated, and it will sometimes quote licensed or private-looking text. Your product has to catch that.

#### [Hugging Face Datasets](https://huggingface.co/docs/datasets) as a catalog

**[Hugging Face Datasets](https://github.com/huggingface/datasets)** is the library and catalog most teams actually open when they need a public dataset, an eval split, or a fine-tune corpus. Browse datasets on the [Hub](https://huggingface.co/datasets), inspect rows in the dataset viewer, then load them with the [`datasets`](https://huggingface.co/docs/datasets) library. Model cards often point at the same Hub ids.

Use it like this:

- **Find what a checkpoint already saw, or a close proxy.** Pretraining mixes are rarely fully published. Instruction and eval sets often are. If you cannot find the data, treat the model as unknown data, not as a clean-room artifact.
- **Load an eval set before you invent one.** Many tasks already have a split you can score. Retrieval-Augmented Generation (RAG) and Evaluation, Tracing, and Guardrails will reuse that habit.
- **Read the license on the dataset card, not only the model card.** A permissive weight license plus a non-commercial dataset is a trap if you fine-tune later.
- **Prefer streaming and documented schemas** over dumping a random CSV into a trainer. The Hub viewer is there so you look at three rows before you write a pipeline.

You do not need [Hugging Face Datasets](https://huggingface.co/docs/datasets) to call a hosted API. You need it the moment you evaluate, compare open-weight models, or even consider an adapter.

#### Instruction tuning, RLHF, and preference data

A pretrained model completes text. An **instruction-tuned** model follows "summarize this" and "return JSON." Teams build that by training on instruction-response pairs, then often on **preference data**: humans or other models ranking answer A versus answer B. **Reinforcement Learning from Human Feedback (RLHF)** is the family of methods that uses those rankings to push the model toward answers people mark as better. [OpenAI](https://openai.com/index/instruction-following/) and [Anthropic](https://www.anthropic.com/research/constitutional-ai-harmlessness-from-ai-feedback) published the pattern; open tooling lives in [Hugging Face TRL](https://github.com/huggingface/trl) and related trainers you will only reach in Shipping if retrieval is not enough.

What you need on the job:

- Chat models you call from an API are already instruction-tuned. That is why a system prompt works at all.
- RLHF and preference tuning change refusals, tone, and "helpfulness." They do not install a knowledge cutoff refresh. New facts still want retrieval or a newer checkpoint.
- If the model is overly sycophantic or overly cautious, you are looking at preference training, not at a bug in your JSON parser. Fix the prompt and the eval first. Fine-tune last.

### When to use a hosted API versus a local model

The practical split is not "cloud versus open source." It is **who runs the GPUs, who sees the bytes, and who you page at 2 a.m.** A hosted API ([OpenAI Platform](https://platform.openai.com/), [Anthropic Console](https://console.anthropic.com/), [Google AI Studio](https://aistudio.google.com/) / [Gemini API](https://ai.google.dev/gemini-api/docs), [Mistral](https://console.mistral.ai/), [DeepSeek](https://platform.deepseek.com/), [Groq](https://groq.com/)) gives you a URL, a key, and a bill. A local (or self-hosted) model means you pull a checkpoint and serve it with [Ollama](https://ollama.com/), [llama.cpp](https://github.com/ggml-org/llama.cpp), [Open WebUI](https://github.com/open-webui/open-webui), or a production engine such as [vLLM](https://github.com/vllm-project/vllm). Many teams do both: API by default, local for offline, sensitive, or cost-smoothed traffic.

Default to a hosted API for the first working loop in the next chapter. Move work local when a constraint below forces it, not because a blog post said "run Llama."

#### Cost, privacy, latency, and lock-in tradeoffs

Write these four down for every feature, not once for the whole company.

- **Cost.** Hosted APIs charge per token (and sometimes per image or audio minute). Local models charge you in GPUs, electricity, and the person who keeps the server up. APIs win at low and spiky volume. Self-hosting wins when you have steady load and a box that would otherwise sit idle. Count tokens either way.
- **Privacy.** If prompts include customer data, source code, or regulated records, read the provider's training and retention terms. Self-hosting keeps bytes on your network, but you still log them. "Local" is not a privacy program by itself.
- **Latency.** A nearby GPU or [Groq](https://groq.com/)-class hosted inference can beat a far-away large model. Streaming hides some wait. Timeouts and fallbacks belong in Shipping; here, measure time-to-first-token on the path you will actually ship.
- **Lock-in.** Proprietary APIs change model ids and prices. Open-weight checkpoints plus an OpenAI-compatible server ([Ollama](https://ollama.com/), [vLLM](https://github.com/vllm-project/vllm), [llama.cpp](https://github.com/ggml-org/llama.cpp)) let you swap weights behind one client. You still lock into prompt format, tokenizer, and evals. Design the client so the provider is a config value.

A useful rule: **prototype on a hosted API, freeze an interface, then decide whether the production path stays hosted, goes local, or splits by data class.**

You will meet the same few names in dashboards and in Hub tags. This is the map, not the SDK tutorial (that is the next chapter).

- **[OpenAI](https://openai.com/).** The default many examples still assume. Use the [OpenAI Platform](https://platform.openai.com/) for APIs, not only [ChatGPT](https://chatgpt.com/). Strong at general text, tools, and image generation. You pay for convenience and you accept their model-id churn.

Prefer them when the job is careful instruction-following on long documents or repos.

- **[Mistral](https://mistral.ai/).** Hosted APIs on [Mistral's platform](https://console.mistral.ai/) plus open-weight checkpoints on the [Hugging Face Hub](https://huggingface.co/mistralai). A practical "same family, two deployment modes" vendor.
- **[DeepSeek](https://www.deepseek.com/).** Hosted [DeepSeek API](https://api-docs.deepseek.com/) (OpenAI-compatible) and open-weight releases such as [DeepSeek-V3](https://github.com/deepseek-ai/DeepSeek-V3). You do not pick a winner in this chapter. You pick a default for tomorrow's first API call, plus a local fallback you can actually install.

## Hosted Models, APIs, and Your First Working Loop

This chapter is the first loop you actually run. You create one or two provider accounts, set a spend cap before the first request, call a model from Python and from JavaScript, and keep the key out of chat logs. We treat the chat apps from the last chapter as products. Here you use the same vendors as APIs: a URL, a key, a model id, and a bill you can read.

Do not collect every console today. Pick a default ([OpenAI Platform](https://platform.openai.com/) is still the path most examples assume), add a second provider only when you have a reason (speed, price, or a model the first host does not offer), and stop when one smoke test passes. Local models wait until Local Models You Can Run Today.

### Create accounts and spend caps before you write prompts

A hosted API will charge you. The failure mode is not a bad first prompt. It is an unbounded key in a script that retries, or a key that leaked into a gist. Create the account, confirm billing, **set a hard cap or alert**, then write the prompt. If the vendor has no monthly cap, set a calendar reminder and a log you look at after the first ten calls.

You need three things written down for each host, not in a screenshot of the dashboard:

- **Where the key lives.** Environment variable name, never a chat, never a committed `.env` in git.
- **The model id you will actually call.** Product names on the marketing site are not ids. Copy the id from the API docs.
- **The spend control.** A usage limit, a prepaid credit, or an explicit "we will check the invoice at $N."

Consumer chat ([ChatGPT](https://chatgpt.com/), [Claude](https://claude.ai/), [Gemini](https://gemini.google.com/)) is a different contract from the API. Do not assume the Plus plan covers [OpenAI Platform](https://platform.openai.com/) usage, or that a Claude.ai transcript will match the [Claude API](https://docs.anthropic.com/).

Open these consoles as APIs, not as chat UIs. Create an organization or workspace you would not mind attaching a card to.

Create a project key, then set billing and usage limits in the platform settings before you install a SDK. This is still the default many snippets assume. You pay for that convenience and you accept model-id churn.
- **[Anthropic Console](https://console.anthropic.com/).** Create a workspace, generate an API key, read [getting started](https://docs.anthropic.com/en/api/getting-started). Prefer this path when the first job is careful instruction-following or a long document, not when you only wanted a ChatGPT clone.
- **[Google AI Studio](https://aistudio.google.com/).** This is how you mint a [Gemini API](https://ai.google.dev/gemini-api/docs) key quickly. Confirm whether you are on AI Studio, [Vertex AI](https://cloud.google.com/vertex-ai), or the consumer [Gemini](https://gemini.google.com/) app. Those are different terms, quotas, and data-use rules. Read the [Gemini API terms](https://ai.google.dev/gemini-api/terms).
- **[Groq](https://groq.com/).** Open the [Groq console](https://console.groq.com/) for a fast, often cheap hosted path. Many Groq models speak an OpenAI-compatible API, which matters when you later put [LiteLLM](https://github.com/BerriAI/litellm) in front. Speed is the reason to add Groq as a second key, not as your only identity provider.
- **[Mistral](https://mistral.ai/).** Use [Mistral's platform](https://console.mistral.ai/) for hosted calls and the [Mistral docs](https://docs.mistral.ai/) for model ids. The same family also ships open-weight checkpoints on the [Hugging Face Hub](https://huggingface.co/mistralai). You do not need the weights today.
- **[DeepSeek](https://www.deepseek.com/).** Create a key on the [DeepSeek platform](https://platform.deepseek.com/) and read the [DeepSeek API](https://api-docs.deepseek.com/). It is OpenAI-compatible, so your first client can be [openai-python](https://github.com/openai/openai-python) with a different base URL. Read the data policy the same way you would for any other host.

One card, one cap, one key is enough for this chapter. A second key is justified when the first host is down, too slow, or too expensive for the smoke test. Five keys on day one is how keys end up in screenshots.

#### [Hugging Face Hub](https://huggingface.co/) tokens and model cards

You will open the [Hugging Face Hub](https://huggingface.co/) even if you never fine-tune. Model ids, licenses, and later local checkpoints live there. Create an account, then a token from the Hub [token docs](https://huggingface.co/docs/hub/en/security-tokens) (`HF_TOKEN` or `HUGGING_FACE_HUB_TOKEN`, not a token pasted into a notebook you will publish). Fine-grained tokens beat classic write tokens for a laptop.

A **[model card](https://huggingface.co/docs/hub/en/model-cards)** is the page you read before you download or cite a checkpoint. It is also how you tell a hosted model id from a Hub repo id. Use the Hub today for three jobs:

- **Find the card for any open-weight name you hear.** "Llama" is not a card. A Hub revision with a license is.
- **Read license and intended use** before you promise a customer you can run it. The [huggingface_hub](https://github.com/huggingface/huggingface_hub) library is how scripts authenticate; you do not need [Transformers](https://github.com/huggingface/transformers) until Local Models You Can Run Today.
- **Keep the token out of git.** Same rule as provider keys. `.gitignore` the env file. Rotate if it ever hits a chat log.

You do not need a Hub token to call [OpenAI](https://platform.openai.com/) or [Anthropic](https://console.anthropic.com/). You need one the moment you pull a gated model, use Hub Inference, or load a dataset in a later chapter.

### Call a model from Python and from JavaScript

The working loop is the same in both languages: load the key from the environment, send a **fixed prompt** to a **recorded model id**, print the **raw** response (not only the assistant string), and record latency plus token usage. Official SDKs exist so you do not hand-roll auth and retries on day one. Install from the vendor's GitHub repository and follow their quickstart. We will not paste a novel of sample code here; the SDK README is the runnable source of truth.

Pick **one** provider and one language for the first green call. Then repeat the same prompt from the other language so you know the model id and the key work outside your favorite runtime. Streaming can wait until the non-streaming call is boring.

#### [openai-python](https://github.com/openai/openai-python) and the [OpenAI Node SDK](https://github.com/openai/openai-node)

**[openai-python](https://github.com/openai/openai-python)** is `pip install openai` and a client that reads `OPENAI_API_KEY`. **[OpenAI Node SDK](https://github.com/openai/openai-node)** is the same API from JavaScript and TypeScript (`OPENAI_API_KEY` again). Follow the [OpenAI quickstart](https://platform.openai.com/docs/quickstart). Chat completions (or the current [Responses API](https://platform.openai.com/docs/api-reference/responses) in the docs) with a short system plus user message is enough.

- Pin a **model id** from the docs, not "the latest GPT." Log that id next to the output.
- Print `usage` (prompt vs completion tokens) on every smoke test. That is how you notice an accidental 8k-token prompt.
- The same client can point at an OpenAI-compatible server later ([Groq](https://console.groq.com/), [DeepSeek](https://api-docs.deepseek.com/), [Ollama](https://ollama.com/), [vLLM](https://github.com/vllm-project/vllm)) by changing `base_url`. Do not do that until the OpenAI endpoint itself works.

If the call fails, read the HTTP status and the body. A 401 is the key. A 429 is rate limit or a spent cap. A 400 is usually the model id or a malformed message list.

#### [anthropic](https://github.com/anthropics/anthropic-sdk-python) Python and [TypeScript](https://github.com/anthropics/anthropic-sdk-typescript) SDKs

**[anthropic](https://github.com/anthropics/anthropic-sdk-python)** (Python) and the [TypeScript SDK](https://github.com/anthropics/anthropic-sdk-typescript) talk to the [Claude API](https://docs.anthropic.com/). The env var is `ANTHROPIC_API_KEY`. Message shape is similar to OpenAI but not identical: system is often a top-level field, not a `"system"` role in the list. Copy that from [getting started](https://docs.anthropic.com/en/api/getting-started), do not guess from an OpenAI snippet.

Use this SDK when Claude is the model you actually want, not as a second way to call GPT. Token counting and long context are documented in the same API docs. Log `usage` the same way you did for OpenAI so the two bills are comparable.

#### [google-genai](https://github.com/googleapis/python-genai) and the [Gemini API](https://ai.google.dev/gemini-api/docs)

**[google-genai](https://github.com/googleapis/python-genai)** is the current Python client for the [Gemini API](https://ai.google.dev/gemini-api/docs). JavaScript lives in [googleapis/js-genai](https://github.com/googleapis/js-genai). Keys from [Google AI Studio](https://aistudio.google.com/) typically go in `GEMINI_API_KEY` or `GOOGLE_API_KEY`; confirm the name in the SDK README, not in a random blog post.

Gemini is worth a first call when you already have a Google account, want a large context window, or need an image in the same request. Confirm the **API** (AI Studio vs [Vertex AI](https://cloud.google.com/vertex-ai)) matches the key you minted. Mixing them produces errors that look like "the model does not exist."

#### [mistralai](https://github.com/mistralai/client-python) Python and [TypeScript](https://github.com/mistralai/client-ts) SDKs

**[mistralai](https://github.com/mistralai/client-python)** and **[mistralai/client-ts](https://github.com/mistralai/client-ts)** wrap the hosted [Mistral](https://docs.mistral.ai/) API. Create the key on [Mistral's platform](https://console.mistral.ai/). This is the SDK pair to use when you picked Mistral as a host, including when you want the same vendor you might later self-host from the [mistralai](https://huggingface.co/mistralai) Hub org.

Do not install this SDK "just in case." Install it when the smoke test's model id is a Mistral id. One successful `chat.complete` (or the current method name in their README) with usage logged is the bar.

#### [DeepSeek API](https://api-docs.deepseek.com/) and OpenAI-compatible clients

The [DeepSeek API](https://api-docs.deepseek.com/) is OpenAI-compatible. Your first DeepSeek call can be [openai-python](https://github.com/openai/openai-python) or the [OpenAI Node SDK](https://github.com/openai/openai-node) with `base_url` set to DeepSeek's endpoint and `DEEPSEEK_API_KEY` (or whatever their docs name). You do not need a DeepSeek-branded SDK to get a green smoke test.

That compatibility is the point of this subsection: **learn one client shape, then retarget the base URL.** [Groq](https://console.groq.com/) works the same way. So will [Ollama](https://ollama.com/) and [vLLM](https://github.com/vllm-project/vllm) in the next chapter. The trap is assuming every field (tool calls, structured output, reasoning tokens) is implemented identically. When something is missing, read DeepSeek's API docs, not OpenAI's, for that host.

### One interface over many providers

The third SDK is when the project starts to rot. Native clients are the right first call. Once you have two hosts, or you know you will swap models in a config file, put a thin adapter in front instead of `if provider ==`. Three tools cover most teams; you pick one, not all three.

#### [LiteLLM](https://github.com/BerriAI/litellm) as a unified API

**[LiteLLM](https://github.com/BerriAI/litellm)** gives you an OpenAI-shaped `completion` call and a model string that names the vendor (`openai/…`, `anthropic/…`, `gemini/…`, `mistral/…`, `deepseek/…`, `groq/…`). Follow [LiteLLM's docs](https://docs.litellm.ai/docs/). Keep using environment variables per provider; LiteLLM reads the usual names.

Use it from Python when the backend is Python and you want one call site. The **proxy** (a local OpenAI-compatible server) is a later Shipping, Cost, and Operations move. Today, the library is enough: same smoke-test prompt, two model strings, compare tokens and latency. If LiteLLM cannot see a key, that is still your env problem, not a reason to hardcode it.

#### [Vercel AI SDK](https://github.com/vercel/ai) for app UIs

**[Vercel AI SDK](https://github.com/vercel/ai)** ([docs](https://ai-sdk.dev/)) is how you stream tokens into a web app without inventing EventSource plumbing. It is for **product UI**, not for a CLI smoke test. Providers plug in as packages; you still hold the vendor keys on the server, never in the browser.

If you are not building a [Next.js](https://nextjs.org/) (or similar) chat surface this week, skip it. If you are, the smoke test is: one route, one model, streamed tokens, key only on the server. Do not start here if you have not yet made a non-streaming call with a native SDK. You will not be able to tell UI bugs from API bugs.

#### [OpenRouter](https://openrouter.ai/) as a model router

**[OpenRouter](https://openrouter.ai/)** is one API key and a catalog of someone else's models. Docs start at [openrouter.ai/docs](https://openrouter.ai/docs). The client can be OpenAI-compatible: change `base_url`, set `OPENROUTER_API_KEY`, pick a model id like `openai/gpt-4o` or `anthropic/claude-…` as OpenRouter lists them.

Use OpenRouter when you want to **try models without creating five vendor accounts**, or when the product should swap vendors behind one bill. You still set a spend cap on OpenRouter itself. You still log the **router** model id, because it is not always the same string the origin vendor uses. Privacy and data-use are OpenRouter's plus the origin's; read both. OpenRouter is not a substitute for learning one native SDK. It is a router you add when the native loop already works.

### Secrets, logging, and a daily working loop

The rest of this book assumes you can rerun one request without drama. That means the key is in the environment, the request is logged in a form you can diff, and a tiny test fails when the model id or the schema breaks.

#### Environment variables, never paste keys into chats

Provider keys are secrets. Treat them like a database password.

- Put them in a local env file that is **gitignored**, or in your shell profile for a personal laptop. `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY` / `GOOGLE_API_KEY`, `GROQ_API_KEY`, Mistral's documented name, `DEEPSEEK_API_KEY`, `HF_TOKEN` / `HUGGING_FACE_HUB_TOKEN`, `OPENROUTER_API_KEY` as needed.
- Load them in process (`os.environ`, `process.env`). SDKs that "also accept `api_key=` in the constructor" still should receive that value from the environment, not from a string literal.
- **Never** paste a live key into [ChatGPT](https://chatgpt.com/), [Claude](https://claude.ai/), [Gemini](https://gemini.google.com/), a GitHub issue, a screenshot of [Cursor](https://cursor.com/), or a prompt file you will commit. If you already did, rotate the key in the console and delete the message.
- CI and teammates get keys from a secret store, not from Slack. Shipping, Cost, and Operations goes deeper on gateways; the rule does not change.

If a tutorial says to drop the key in the notebook: close the tutorial. The Hub [token docs](https://huggingface.co/docs/hub/en/security-tokens) and every serious SDK README assume an environment variable.

#### A repeatable smoke test you run after every model change

A **smoke test** is a script you run on purpose, not a vibe check in a chat window. Check it into git. It should take under a minute and fail loudly.

1. **Call** one recorded model id with a prompt stored in the repo (a single sentence is enough: "Reply with the word pong and nothing else.").
2. **Inspect** the raw payload: text, finish reason, usage, request id if the host sends one.
3. **Check** one assertion: the text is non-empty, or it equals `pong`, or it is valid JSON if you asked for JSON. Do not assert poetry quality here.
4. **Log** latency, prompt tokens, completion tokens, model id, and provider. A one-line CSV or JSONL in a gitignored `logs/` directory is enough.
5. **Change one thing** (model id, temperature, host, or the prompt file) and rerun. If you changed the host, you should only have changed config, not the assertion.

Run this after you bump a SDK, after you rotate a key, and after someone "just switches to the new model" in a dashboard. When the smoke test is green, you have a working loop. Prompting, Context, and System Instructions is where that prompt gets serious. Next in this book is **Local Models You Can Run Today**, where the same OpenAI-shaped client can point at a process on your machine.

### Summary: Hosted Models, APIs, and Your First Working Loop

Hosted GenAI starts with an account, a **spend cap**, and a key in an environment variable, not with a clever prompt in a consumer chat. Open [OpenAI Platform](https://platform.openai.com/), [Anthropic Console](https://console.anthropic.com/), [Google AI Studio](https://aistudio.google.com/), [Groq](https://console.groq.com/), [Mistral](https://console.mistral.ai/), or [DeepSeek](https://platform.deepseek.com/) as APIs; keep a [Hugging Face Hub](https://huggingface.co/) token for cards and later downloads. Call once with [openai-python](https://github.com/openai/openai-python) or the [OpenAI Node SDK](https://github.com/openai/openai-node), and again with [anthropic](https://github.com/anthropics/anthropic-sdk-python), [google-genai](https://github.com/googleapis/python-genai), [mistralai](https://github.com/mistralai/client-python), or an OpenAI-compatible [DeepSeek API](https://api-docs.deepseek.com/) client when that is the host you picked. When the third SDK appears, use [LiteLLM](https://github.com/BerriAI/litellm) in the backend, the [Vercel AI SDK](https://github.com/vercel/ai) for a UI, or [OpenRouter](https://openrouter.ai/) as a router — not all three on day one. Log usage, never paste keys into chats, and keep a smoke test you rerun after every model change. Next is **Local Models You Can Run Today**, where you install a runner and keep the same working loop.

## Local Models You Can Run Today

This chapter moves the smoke test from a hosted URL onto a process you start yourself. You install one runner, pull one small checkpoint, and call it with the same client from Hosted Models, APIs, and Your First Working Loop. The model id changes. The assertion stays the one you already trust.

A **local model** is weights on your disk plus a server that turns a prompt into tokens. [Ollama](https://ollama.com/) is the runner you install first. [llama.cpp](https://github.com/ggml-org/llama.cpp) is the runner you open when you need the GGUF file and the flags. [Open WebUI](https://github.com/open-webui/open-webui) is a chat front end in front of that server. [vLLM](https://github.com/vllm-project/vllm), [SGLang](https://github.com/sgl-project/sglang), and [Text Generation Inference](https://github.com/huggingface/text-generation-inference) are for a GPU box with concurrent users. Get one laptop loop green before you read those.

[Ollama](https://ollama.com/) also sells a cloud path: tags that end in `-cloud`, and `https://ollama.com/v1` with `OLLAMA_API_KEY`. That path is a hosted API. This chapter is the local server at `http://localhost:11434`.

### Install a local runner in under an hour

Give yourself one machine, one runner, and one small model. The hour includes the download. It does not include shopping for a GPU.

Write down three facts before the pull finishes:

- **Where the weights live.** [Ollama](https://ollama.com/) stores models under its own directory (typically `~/.ollama`). [Hugging Face](https://huggingface.co/) downloads land in the Hub cache (`~/.cache/huggingface`). These are gigabytes. Delete tags you are not using.
- **The exact model id you will call.** An [Ollama library](https://ollama.com/library) tag, or a Hub repo plus a GGUF filename. "Llama" is still not an id.
- **The base URL of the server.** Local [Ollama](https://docs.ollama.com/api/openai-compatibility) is `http://localhost:11434/v1`. [llama.cpp](https://github.com/ggml-org/llama.cpp)'s server defaults to port `8080`. Your smoke test from the last chapter should only need a new base URL and a new model id.

#### [Ollama](https://ollama.com/) for everyday local chat and APIs

Install [Ollama](https://ollama.com/download) from the official download page, then confirm the process is up. The [Ollama](https://github.com/ollama/ollama) repository is the source; the [API introduction](https://docs.ollama.com/api/introduction) is the contract.

The first loop:

1. Open the [Ollama library](https://ollama.com/library) and pick a **small instruct** tag that fits your RAM. A model in the 3B–8B class is a smoke test. A 70B-class tag is a different project.
2. `ollama pull` that exact tag. `ollama list` should show it. `ollama run` is the terminal chat if you want to see tokens before you write code.
3. Leave the server running. It listens on port **11434**. The native API is `http://localhost:11434/api`. The OpenAI-compatible API is `http://localhost:11434/v1`.
4. Call it with [openai-python](https://github.com/openai/openai-python) or the [OpenAI Node SDK](https://github.com/openai/openai-node). Set `base_url` to `http://localhost:11434/v1/` and `api_key` to any non-empty string such as `ollama`. Local [Ollama](https://docs.ollama.com/api/openai-compatibility) ignores that key. The client library still requires one.
5. Send the same fixed prompt as your hosted smoke test ("Reply with the word pong and nothing else." is still enough). The `model` field is the library tag you pulled, not a hosted id.

Read the [OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility) page before you assume every field exists. Chat completions, streaming, JSON mode, and tools are in the subset. `tool_choice` and logprobs are not. When a later tool-calling chapter fails on localhost, check that page before you rewrite the prompt.

`ollama signin` and `OLLAMA_API_KEY` attach you to [Ollama](https://ollama.com/)'s cloud. Skip them until the local tag answers `pong`.

#### [llama.cpp](https://github.com/ggml-org/llama.cpp) and GGUF when you need control

**[GGUF](https://huggingface.co/docs/hub/gguf)** is the single-file checkpoint format [llama.cpp](https://github.com/ggml-org/llama.cpp) loads. Quantization is in the filename: `Q4`, `Q5`, `Q8`, and other labels. A smaller quant fits more machines and drops more quality. You record the file you ran. You do not "run Llama" and hope the quant was fine.

Use [llama.cpp](https://github.com/ggml-org/llama.cpp) when [Ollama](https://ollama.com/) hides a knob you need: which GGUF file, how many GPU layers, context length, or a build for a specific CPU. Install from the repository README (a package, a release binary, or a build). The current commands are:

- `llama cli -hf <repo>` runs a GGUF straight from the [Hugging Face Hub](https://huggingface.co/).
- `llama serve -hf <repo>` starts the OpenAI-compatible HTTP server. The server README documents the routes, including chat completions, and the default port **8080**: [tools/server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).

Point the same OpenAI client at `http://localhost:8080/v1` and set `model` to the id the server reports. Keep the smoke-test prompt. Change the base URL and the model id, then rerun.

On a Mac, the Metal build is the Apple Silicon path. On NVIDIA, a CUDA build offloads layers to the GPU. On a machine with neither, you are on CPU: it will answer, and it will be slow. That is a successful smoke test if the assertion passes. It is a poor production plan. The hardware section below is where you choose on purpose.

#### [Open WebUI](https://github.com/open-webui/open-webui) as a local ChatGPT-style front end

**[Open WebUI](https://github.com/open-webui/open-webui)** is a browser chat in front of a runner. It does not contain a model. Follow the [quick start](https://docs.openwebui.com/getting-started/quick-start/) and the [Ollama connection guide](https://docs.openwebui.com/getting-started/quick-start/connect-a-provider/starting-with-ollama/). The usual shape is Docker, the UI on port **3000**, and the runner still on **11434**.

If both run on one machine and Open WebUI is in Docker, the container reaches the host at `http://host.docker.internal:11434`, which is why the quick start adds that host mapping. From a non-Docker install, the URL is `http://localhost:11434`. Settings → Admin → Connections is where you confirm the runner and pull a tag. The [connection docs](https://docs.openwebui.com/getting-started/quick-start/connect-a-provider/) also let you attach a hosted OpenAI-compatible provider beside the local one. Selecting the local model in the chat box is what keeps the prompt on your machine.

Open WebUI stores chats in its data volume. Local inference does not make that database disappear. Treat the volume like a log: it has prompts in it. Set `WEBUI_SECRET_KEY` once, as the quick start says, so a recreated container does not log everyone out.

Use the UI to see the model. Keep the scripted smoke test as the thing you rerun after a pull. A pleasant chat is not the assertion.

### Pull, test, and swap models without rewriting your app

The app should not care whether the weights came from [Ollama](https://ollama.com/), [llama.cpp](https://github.com/ggml-org/llama.cpp), or a GPU server. It should care about a **base URL**, a **model id**, and the **same assertion**. Swapping models means changing those two config values and rerunning the smoke test. It does not mean a new HTTP stack.

#### [Hugging Face Transformers](https://github.com/huggingface/transformers) and Hub as the catalog

The **[Hugging Face Hub](https://huggingface.co/models)** is still the catalog. The **[Transformers](https://github.com/huggingface/transformers)** library ([docs](https://huggingface.co/docs/transformers)) is how Python loads a Hub repo as tensors: safetensors checkpoints, tokenizers, and `pipeline` or `generate` calls. You already created a Hub token in the last chapter. Use it here when a repo is gated. Read the [model card](https://huggingface.co/docs/hub/en/model-cards) for license, size, and the exact revision before you download.

Three catalogs get mixed together. Keep them separate:

- **[Ollama library](https://ollama.com/library) tags** (`something:7b`) for `ollama pull` and for `model` on port 11434.
- **GGUF repos** on the Hub, for `llama serve -hf` and for any runner that expects [GGUF](https://huggingface.co/docs/hub/gguf). The quant is a file in that repo.
- **Transformers repos** (usually safetensors) for [Transformers](https://github.com/huggingface/transformers), and later for [vLLM](https://github.com/vllm-project/vllm) or [SGLang](https://github.com/sgl-project/sglang). A GGUF repo id will not load in Transformers just because the brand name matches.

Open Transformers when you need Python control, a custom generation loop, or the adapter work in Shipping, Cost, and Operations. For the daily app, stay on an OpenAI-compatible server and swap the id in config. Loading weights inside every web request with Transformers is how you run out of memory on the first concurrent user.

#### OpenAI-compatible local endpoints

You already learned one client shape. Local serving is that shape with a new base URL.

| Runner | Base URL | What you put in `model` |
| --- | --- | --- |
| [Ollama](https://docs.ollama.com/api/openai-compatibility) | `http://localhost:11434/v1` | The library tag you pulled |
| [llama.cpp](https://github.com/ggml-org/llama.cpp) `llama serve` | `http://localhost:8080/v1` | The id the server loaded |
| [vLLM](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/) | `http://localhost:8000/v1` | The Hub repo you passed to `vllm serve` |

The working loop after every swap:

1. **Call** the recorded model id with the prompt file from the hosted smoke test.
2. **Inspect** the raw payload: text, finish reason, and usage if the server sent it. Local servers sometimes omit token counts. Log the absence. Do not invent a number.
3. **Check** the same assertion as yesterday (`pong`, non-empty, or valid JSON). A new model that fails `pong` is a model problem or a template problem. Raise the size one step, or confirm you pulled an **instruct** tag, before you edit the prompt.
4. **Change one thing.** Another tag, another base URL, or a larger context setting. Rerun.

Context length is the setting that surprises people. Hosted models often accept a long window by default. A local runner may default much shorter, and a long window costs RAM on top of the weights (the KV cache). If the server errors on context, shorten the prompt or raise the runner's context flag, then rerun the same assertion. Sampler folklore waits until Common Challenges and Debugging Tips.

[LiteLLM](https://github.com/BerriAI/litellm) can name an Ollama model in its model string once this direct call works. Prove localhost with the OpenAI client first, so a router bug is not your first local failure.

### When local is no longer enough

A laptop runner is enough for one developer, a smoke test, and offline or sensitive drafts. It runs out of room when several people hit it at once, when the context is long and the latency budget is tight, or when the model that passes evals does not fit in the machine on your desk. That is a serving problem. The fix is an engine built for concurrent requests, on a GPU that can hold the weights.

Stay on [Ollama](https://ollama.com/) or [llama.cpp](https://github.com/ggml-org/llama.cpp) while you are still the only client. Move when you can point at a queue, a GPU, and a bill for the box.

#### [vLLM](https://github.com/vllm-project/vllm) for high-throughput serving

**[vLLM](https://github.com/vllm-project/vllm)** serves Hub checkpoints (the Transformers-style repos, not a random GGUF tag) with continuous batching so many requests share the GPU. The [quickstart](https://docs.vllm.ai/en/stable/getting_started/quickstart/) is `vllm serve <hub-repo>`. The [OpenAI-compatible server](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/) listens on port **8000** by default. Point the same client at `http://localhost:8000/v1`. If you set `--api-key`, the client must send it. The vLLM docs also say that key covers the `/v1` routes and does not, by itself, lock every other path on the process. Put the server on a private network.

vLLM is the default you reach for on an NVIDIA GPU when [Ollama](https://ollama.com/) was fine on a laptop and is now the bottleneck. Install it on that GPU machine, not on a CPU laptop "to learn the flags." Your smoke test is the same prompt, the Hub repo as the model id, and the same assertion.

#### [SGLang](https://github.com/sgl-project/sglang) and [Text Generation Inference](https://github.com/huggingface/text-generation-inference)

**[SGLang](https://github.com/sgl-project/sglang)** is the other high-throughput engine you should know. Its [OpenAI-compatible API](https://docs.sglang.io/docs/basic_usage/openai_api_completions) speaks chat completions and completions, and it applies the chat template from the Hub tokenizer. Reach for SGLang when you want that stack's serving speed or its structured-generation path, and you are already on a datacenter GPU. The client change is still a base URL and a model id.

**[Text Generation Inference](https://github.com/huggingface/text-generation-inference)** (TGI) is [Hugging Face](https://huggingface.co/)'s serving server, with an OpenAI-compatible messages API documented in the [TGI HTTP reference](https://huggingface.co/docs/text-generation-inference/reference/api_reference). As of 11 December 2025, Hugging Face put TGI in **maintenance mode** and tells new [Inference Endpoints](https://huggingface.co/docs/inference-endpoints/engines/tgi) deployments to use vLLM or SGLang. Learn TGI so you can read a deployment you inherited. Start a new server on [vLLM](https://github.com/vllm-project/vllm) or [SGLang](https://github.com/sgl-project/sglang).

#### Choosing CPU, Apple Silicon, and NVIDIA GPU paths

Pick the path from the chip in front of you, then from how many people will call it.

- **CPU.** [llama.cpp](https://github.com/ggml-org/llama.cpp) with a small GGUF quant is the honest path. [Ollama](https://ollama.com/) on CPU is the same idea with a library tag. Expect a slow smoke test that still proves the client. A CPU box serving a team will miss latency budgets. Quantize down until the process stays in RAM. If it swaps to disk, the model is too big for this machine.
- **Apple Silicon.** Unified memory is the budget: weights plus KV cache have to fit in that RAM, next to the rest of macOS. [Ollama](https://ollama.com/) and [llama.cpp](https://github.com/ggml-org/llama.cpp) use Metal here, and they are the default install. **[MLX](https://github.com/ml-explore/mlx)** and **[MLX LM](https://github.com/ml-explore/mlx-lm)** are Apple's own stack: `mlx-lm` pulls MLX checkpoints, including the [mlx-community](https://huggingface.co/mlx-community) org on the Hub, and runs them on the GPU in the chip. Use MLX when you want that format. Use Ollama when you want the OpenAI-compatible server from the previous section. vLLM and TGI are datacenter-GPU engines; they are the wrong first install on a Mac.
- **NVIDIA GPU.** This is where throughput engines pay off. One developer can stay on [Ollama](https://ollama.com/) or [llama.cpp](https://github.com/ggml-org/llama.cpp) with CUDA. A shared service should move to [vLLM](https://docs.vllm.ai/en/stable/getting_started/quickstart/) or [SGLang](https://docs.sglang.io/). The weights still have to fit in VRAM, and the KV cache grows with context length and with concurrent sequences. If the process dies on allocate, you picked too large a model, too long a context, or too many parallel requests. Lower one of those and rerun the smoke test before you change the prompt.

Whatever the chip, rerun the hosted-chapter smoke test after the move. A faster server that fails `pong` is still a failed swap.

### Summary: Local Models You Can Run Today

Local GenAI is a checkpoint on disk and a server you can restart. Install [Ollama](https://ollama.com/), pull one small instruct tag, and call `http://localhost:11434/v1` with the OpenAI client you already trust. Drop to [llama.cpp](https://github.com/ggml-org/llama.cpp) and a named [GGUF](https://huggingface.co/docs/hub/gguf) file when you need the quant and the flags. Put [Open WebUI](https://github.com/open-webui/open-webui) in front when you want a chat box, and keep the script as the smoke test. The [Hugging Face Hub](https://huggingface.co/models) and [Transformers](https://github.com/huggingface/transformers) are the catalog and the Python loader; the app should still talk to an OpenAI-compatible base URL so a swap is a config change. When one laptop is no longer enough, serve on an NVIDIA GPU with [vLLM](https://github.com/vllm-project/vllm) or [SGLang](https://github.com/sgl-project/sglang). Treat [Text Generation Inference](https://github.com/huggingface/text-generation-inference) as a server you may inherit, since Hugging Face has it in maintenance mode. On Apple Silicon, stay with Ollama, llama.cpp, or [MLX LM](https://github.com/ml-explore/mlx-lm). Next is **Prompting, Context, and System Instructions**, where that fixed prompt becomes a system prompt, a JSON prompt, and a file you can commit.

## Prompting, Context, and System Instructions

The smoke test so far is one sentence: "Reply with the word pong and nothing else." This chapter turns that sentence into instructions you can keep. You write a **system prompt**, put the task in the user turn, name the output shape, and store the prompt in Git. The context window is the budget those pieces spend. A large wiki still waits for Retrieval-Augmented Generation (RAG). A schema the parser must trust waits for Structured Outputs and Tool Calling.

Run the same hosted or local client. Change the prompt file, rerun, and tighten the assertion from "non-empty" to "matches this shape."

### Write instructions the model can follow

A **prompt** is the whole request: durable rules, the task, the evidence, and the shape of the answer. The model does not see your intent. It sees that text, in order, inside the window. If a colleague with no extra context would hesitate, the model will too. That is the test [Anthropic](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/system-prompts) uses in its prompting guide, and it works for every host in this book.

One change per rerun. Edit the rule, or the example, or the document you attached. A prompt that "feels better" and a new model id in the same commit is two experiments.

#### System prompts

A **system prompt** is the instruction that should hold on every turn: the job, the constraints, the output shape, and what to do when the input is missing. The user's question is not the system prompt. The system prompt is the part you would be angry to see a customer rewrite.

Put it in the slot the API actually treats as instructions:

- **[Anthropic](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/system-prompts).** Top-level `system` on the Messages API, not a `"system"` item you copied from an OpenAI snippet. The same guide is where Claude's prompting notes live: clear output constraints, a role in one or two sentences, and XML tags when instructions, examples, and data share one request.
- **[Gemini](https://ai.google.dev/gemini-api/docs/text-generation).** `system_instruction` on the client. [Prompt design strategies](https://ai.google.dev/gemini-api/docs/prompting-strategies) say the role, the constraints, and the format belong there, or at the start of the user prompt.
- **[OpenAI](https://developers.openai.com/api/reference/resources/chat).** Durable instructions are a `developer` message on current models, or the `instructions` field on the [Responses API](https://platform.openai.com/docs/api-reference/responses). Details are in the next section. A `system` role still appears in older chat examples.

Write the system prompt so you can read it in one screen. A novel about persona spends the window and hides the one rule that matters. Name the missing-input behavior in a sentence: "If the ticket has no product name, return `unknown`. Do not guess." Then prove it. Send a fixture with the product name removed and assert `unknown`.

#### System, developer, and user roles

Roles are how the request separates **instructions you control** from **text the user controls**.

- **User.** The task, the question, and the document. If a customer, a web page, or a ticket can edit this text, treat it as data. Say so in the instruction: the block is evidence, not a new rule. Prompt injection is a later chapter (Evaluation, Tracing, and Guardrails). The habit starts here.
- **Assistant.** Earlier replies from the model. Leave them as history. Hand-written assistant turns are few-shot examples, and they belong in the prompt file on purpose.
- **System.** The name [Anthropic](https://docs.anthropic.com/en/api/getting-started) and many local chat templates still use for durable instructions. [Gemini](https://ai.google.dev/gemini-api/docs/text-generation) calls the same idea a system instruction.
- **Developer.** On [OpenAI](https://developers.openai.com/api/reference/resources/chat), from o1 onward, a `developer` message is the instruction channel you own. It replaces `system` for those models. Sending `system` is often accepted and treated as `developer`. Read the model page before you assume you still have two different slots. The [OpenAI Model Spec](https://model-spec.openai.com/) calls this the chain of command: developer instructions outrank user text.

Local runners follow the checkpoint's chat template. [Ollama](https://docs.ollama.com/api/openai-compatibility) and [llama.cpp](https://github.com/ggml-org/llama.cpp) will pass a system or developer role through only if that template has a place for it. If a small instruct model ignores the rule and answers the user text anyway, inspect the template and the rendered prompt before you add more adjectives.

Keep one instruction channel. Rules in the developer message, the same rules repeated in the user message, and a third copy in a README the model never sees will drift. The file you load into the instruction slot is the one you test.

#### Splitting work, delimiters, and output contracts

One request, one job. "Classify the ticket, then draft the reply, then score your draft" is three calls, or three labeled blocks with three checks. A single paragraph that asks for all three is how the smoke test becomes a vibe check.

**Delimiters** mark data apart from instructions. Name the fence in the instruction and wrap the payload in it. [Anthropic's prompting guide](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/system-prompts) uses XML tags (`<ticket>`, `<examples>`). [Gemini's prompting strategies](https://ai.google.dev/gemini-api/docs/prompting-strategies) accept XML-style tags or Markdown headings, and they want one style inside a single prompt. Pick one, use it on every fixture, and do not nest a second convention "for clarity."

For a long document, put the document first and the question after it. Both the Claude long-context notes and the Gemini long-context notes ask for that order so the question is the last thing the model reads. The durable rules stay in the system or developer slot, not buried under the document.

An **output contract** is the assertion in words. "Reply with the word pong and nothing else" was a contract. The next one is the same kind of sentence: "Return exactly three lines: a title, a severity of `low` or `high`, and one sentence. No preamble." Assert those three lines in the smoke test. When the contract is a schema a program must parse, you are at the door of the next chapter. Stay with a sentence contract while you are still changing the wording.

#### Few-shot examples that help instead of confuse

A **few-shot** prompt shows one to a handful of input/output pairs. Use them when the format is easier to show than to describe: a house style, a closed label set, a layout. [Anthropic](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/system-prompts) suggests a few diverse examples wrapped so they cannot be mistaken for the live task. [Gemini](https://ai.google.dev/gemini-api/docs/prompting-strategies) makes the same split: zero-shot when the instruction is enough, few-shot when you are regulating format.

Make every example obey the contract. A sloppy sample teaches the sloppy shape, and your assertion will fail for a reason that looks like "the model got worse." Cover an edge you actually hit (empty field, two languages), not five identical happy paths. When the model keeps making one specific mistake, add one counterexample that shows the correction.

Stop adding examples when the prompt is mostly demonstrations. A pile of pairs belongs in an eval set, which Evaluation, Tracing, and Guardrails will score, or in [DSPy](https://github.com/stanfordnlp/dspy) later in this chapter. Forty examples on every call spend the window and the bill. Three examples in the prompt file are a format. A hundred rows on disk are a dataset.

### JSON prompts

A JSON prompt is the instruction written as an object: task, rules, output shape, and input. The model then follows named fields. "Reply in JSON" is a separate decision about the answer. You can do either, or both.

#### Write the prompt as JSON, not only the answer

Prose hides the rule in a paragraph. A JSON prompt puts each rule in a field you can diff:

```json
{
  "task": "classify",
  "labels": ["billing", "access", "other"],
  "rules": ["choose one label", "no preamble"],
  "input": "I was charged twice for the same seat."
}
```

Load that object in the smoke test. Fill `input` from a fixture. Keep `task`, `labels`, and `rules` stable across runs so a failure points at the input or the model, not at a sentence you reworded in the same commit.

The file you commit uses fake `input`. A customer ticket, a secret, or a production log stays out of Git, same as an API key. The hosted-chapter rule still applies: the prompt file is not a place to paste a live credential "so the model can see the header."

JSON as the answer is the contract on the way out: "Return one object with `label` and `reason`." Parse it in the smoke test with a strict parser. A trailing comma or a sentence before the brace fails the run. That failure is the signal to move to structured outputs, not to add "please really return JSON" for the fourth time.

#### When JSON prompts are enough versus structured outputs

A JSON prompt plus a strict parse is enough when a person could also check the object, the schema is small, and a retry is acceptable. Support macros, a classifier with three labels, and a fixture suite you run by hand all live here.

Move on when a program will trust the types. A database write, a tool argument, or a form field that must be an integer is Structured Outputs and Tool Calling. That chapter covers native structured outputs on the hosted APIs, [Instructor](https://github.com/567-labs/instructor), and constrained generators. JSON mode on some APIs (valid JSON, any shape) sits between the two: it stops preamble, and it does not stop a missing field. Use it as a bridge. Do not treat it as a schema.

The smoke test decides. If `json.loads` plus a check for the required keys passes all week, stay in this chapter's pattern. If the same keys come back as strings one day and numbers the next, stop editing the prompt and pick up the next chapter.

### Context windows as a budget

Chapter 1 defined the **context window**: every token of instructions, history, documents, tool results, and the reply still streaming. You pay for the prompt and you pay again for the completion. This section is how you spend that budget on purpose.

Count with the provider's tokenizer before you celebrate a clever prompt. Log prompt tokens on the smoke test, hosted or local. A prompt that grew from a few hundred tokens to several thousand is a budget change. Review it like a dependency bump.

#### What to put in the prompt versus retrieve later

Keep in the prompt what the model must see on this call:

- The system or developer rules.
- The current task.
- The one document, diff, or ticket the task is about, when it fits and the model needs all of it.
- A few examples that define the format.

Leave for retrieval anything that is large, stale-prone, or only sometimes relevant: a wiki, a pile of PDFs, a year's tickets. Retrieval-Augmented Generation (RAG) is the chapter that fetches the paragraph. Pasting the wiki "so the model has context" fills the window and buries the instruction. Coding Agents and Skills is where a repo turns into tools and a map, which is the same decision for source code.

Stable rules at the front of the request are also what prompt caches reuse. [Anthropic prompt caching](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching) builds the prefix from tools, then system, then messages. Shipping, Cost, and Operations is where you turn that into a bill. Here, keep the system prompt byte-stable and put the varying ticket at the end.

#### Summaries, memory notes, and stale context

When the window fills, replace old turns with a **summary you wrote**, or drop them. Check the request that actually left your process. A client library that silently trims the start will trim the system prompt first if you stacked history above it. Put instructions first. Trim history.

A **memory note** is a short file or message: decisions, names, constraints, dates. It is not the transcript. Date it. A note that says "the API is v1" will outrank the code you shipped last week, because the model can see the note and cannot see the calendar. Rebuild the note when the source changes. A summary is a cache with an expiry.

Agents and Multi-Step Workflows goes further under memory engineering: what to store, what to forget, what to retrieve. Until then, prefer the current document over a month-old paraphrase, and prefer a short note over an unbounded chat log.

### Prompt files you can version in Git

A prompt you only have in a chat window will be different tomorrow. The smoke test should load a file.

#### Keep prompts next to code, not in a chat history

Put the system prompt and the JSON prompt in the repo, next to the test that calls them: `prompts/classify.md` or `prompts/classify.json`. One task, one file. The smoke test reads the file, sends it, and checks the contract.

Review the diff the way you review code. A wording change is a behavior change. Record the model id and the token count in the test log, not inside the text the model reads. A line like "You are running on gpt-…" becomes a lie the day you point the same file at [Ollama](https://ollama.com/).

Fixtures sit beside the prompt, with fake input. Production text stays in a gitignored path. The loop is the one you already have:

1. **Call** the recorded model id with the prompt file and one fixture.
2. **Inspect** the raw text and the prompt-token count.
3. **Check** the contract: three lines, a label from the list, or a JSON object with the required keys.
4. **Change one thing** in the file and rerun. Commit the file and the assertion together when the run is green.

#### [DSPy](https://github.com/stanfordnlp/dspy) when prompts should be optimized, not hand-tuned forever

**[DSPy](https://github.com/stanfordnlp/dspy)** ([docs](https://dspy.ai/)) is the point where you stop rewording by hand. You write the task as a program with a signature, you score outputs with a metric, and an optimizer proposes instructions and few-shot demos. The project's line is to program the model call, then compile the prompts.

Use it when three manual edits no longer move a score you can explain, and you have examples. A handful can start `BootstrapFewShot`. Instruction search such as [MIPROv2](https://dspy.ai/current/api/optimizers/MIPROv2/) or [GEPA](https://dspy.ai/current/api/optimizers/GEPA/overview/) wants a real metric and a held-out set, because a prompt optimizer will fit a tiny train set and look brilliant on it. Save the compiled program and commit that artifact next to the hand-written prompt so the diff shows what the search changed.

Skip DSPy while the contract is still "return three lines" and you have no score. A file plus a smoke test is the whole tool. Skip it when the failure is types and parsing: that is structured outputs, and it is cheaper than a search over wordings. The metric you would hand DSPy is the same assertion style as Evaluation, Tracing, and Guardrails. Build a score you believe before you let an optimizer maximize it.

### Summary: Prompting, Context, and System Instructions

A prompt is durable rules, a task, evidence, and an output contract, loaded from a file and checked by the smoke test. Put the rules in the **system** slot ([Anthropic](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/system-prompts), [Gemini](https://ai.google.dev/gemini-api/docs/text-generation) system instructions) or the **developer** slot on current [OpenAI](https://developers.openai.com/api/reference/resources/chat) models, and put user text behind a delimiter. A few examples teach a format. A **JSON prompt** names the fields you would otherwise bury in prose, and it is enough until a program must trust the types. Spend the context window on this call's rules and this call's document. Summarize or retrieve the rest, and date every memory note so it can go stale on purpose. When hand edits stall and you have a metric, compile with [DSPy](https://github.com/stanfordnlp/dspy). Next is **Coding Agents and Skills**, where those prompt files meet a repo, an agent, and a `SKILL.md` you can install.

## Coding Agents and Skills

A coding agent is a model in a loop with your repo: it can read files, edit them, and run commands. The prompt file from the last chapter still matters. What changes is the default behavior around that prompt: which agent you trust for a week, which `SKILL.md` it loads, and which hook runs even when the model skips a step.

Pick one agent. Point it at a repo you can reset. Give it one task whose definition of done is a test, a small diff, or a page you can open. Install one skill and edit it. Add a hook only when a written instruction failed to make the action happen.

### Pick a coding agent and stay with it for a week

Switching tools every afternoon teaches you the install screens. Staying with one agent for a week teaches you how it fails in your repo. Write down the agent, the model id, and the task. At the end of the week you should be able to say what it edits well, what it refuses to check, and which file you had to add so the next session starts warmer.

#### [Cursor](https://cursor.com/), [Claude Code](https://github.com/anthropics/claude-code), [Codex](https://github.com/openai/codex), and [GitHub Copilot](https://github.com/features/copilot)

These four are enough to choose from. Use the one your team already pays for, then learn its rules file and its skill directory. Do not collect all four on day one.

- **[Cursor](https://cursor.com/).** The editor this book is written beside. Agent chat, project rules, [skills](https://cursor.com/docs/skills), and [hooks](https://cursor.com/docs/hooks) live in the repo. Stay here for a week if your work is the editor: diffs, tests, and a browser on the app you are changing.
- **[Claude Code](https://github.com/anthropics/claude-code).** Anthropic's terminal agent. It reads `CLAUDE.md`, loads skills and plugins, and runs [hooks](https://docs.anthropic.com/en/docs/claude-code/hooks) from `.claude/settings.json`. Stay here for a week if you want a long repo task from the shell, with a transcript you can scroll.
- **[Codex](https://github.com/openai/codex).** OpenAI's coding agent, CLI and IDE. It reads `AGENTS.md` and can install skills as plugins. Stay here for a week if your hosted default is already OpenAI and you want the agent on that same account.
- **[GitHub Copilot](https://github.com/features/copilot).** Inline suggestions plus an agent in the editor and a CLI. Custom instructions and hooks live under `.github/`. Stay here for a week if the repo is already on GitHub and the team will not approve a second vendor.

The week-long loop is the same on each: one task, one rules file, one test command, one review of the diff. If the agent cannot run the tests, fix that before you blame the model.

#### [Aider](https://github.com/Aider-AI/aider) and [OpenCode](https://github.com/sst/opencode) in the terminal

**[Aider](https://aider.chat/)** ([repo](https://github.com/Aider-AI/aider)) is a terminal pair programmer that maps a repo, edits files, and commits. You bring the model: hosted or a local OpenAI-compatible server from the local-models chapter. Use it when you want the git history to be the transcript and you do not want an IDE product in the middle.

**[OpenCode](https://github.com/sst/opencode)** is a terminal coding agent with its own plugin directory (`.opencode/`). Use it when you want a client you can point at more than one model provider, including a local one, and you are willing to live in the shell for the week.

Both are the right week if your definition of done is a commit and a test command. They are a poor week if the task is a visual UI change and you have no way to open the page. Pair them with a browser check, or pick Cursor for that task.

#### What [Continue](https://github.com/continuedev/continue) was, and why you should not start a new project on it

**[Continue](https://continue.dev/)** was an open-source coding agent: a VS Code extension, a JetBrains plugin, and a CLI, model-agnostic, Apache-2.0. Cursor acquired it. The [repository](https://github.com/continuedev/continue) is read-only and no longer maintained. The project shipped a final 2.0.0 release and stopped. The code remains available to read and fork.

Do not start a new project on Continue. A new repo wants an agent that still ships skills, hooks, and fixes. If you already run Continue, treat the install as frozen: pin the version you have, and plan a move to one of the agents above rather than filing issues upstream. The acquisition is the reason the docs went quiet. It is not a reason to copy Continue's config into a greenfield repo.

### Agent Skills that change the default behavior

A **skill** is a folder the agent can load when a task matches: instructions, and sometimes scripts or templates. It changes the default behavior without you pasting the same prompt every session. The open format is [Agent Skills](https://github.com/agentskills/agentskills). [Cursor](https://cursor.com/docs/skills) loads it. Claude Code, Codex, and the [skills.sh](https://www.skills.sh/) installer do too.

The agent sees the skill's name and description first, and pulls the body when the task fits. A vague description means the skill never fires. A description that says when to use it is the whole discovery mechanism.

#### `SKILL.md` as the skill file

Every skill is a directory with a **`SKILL.md`** file. YAML frontmatter holds at least `name` and `description`. The markdown below is the procedure. Optional `scripts/`, `references/`, and `assets/` sit beside it. Cursor's [skill format](https://cursor.com/docs/skills) adds fields such as `paths` (only surface the skill on matching files) and `disable-model-invocation` (only run when you type `/skill-name`).

Put project skills in the repo so they review like code:

- `.agents/skills/<name>/SKILL.md` for the shared layout
- `.cursor/skills/` when the skill is Cursor-specific
- `.claude/skills/` or `.codex/skills/` when you are on those agents

User-level copies (`~/.cursor/skills/`, `~/.claude/skills/`) stay on your machine. They will not be on a teammate's laptop or a cloud agent unless you commit the project copy. Commit the project copy.

Write the description as the trigger: "Use when the user asks to add a feature and no failing test exists yet." Write the body as steps the agent can follow, including the command to run. A skill that says "write clean code" does not change the diff. A skill that says "add a failing test, then the change, then re-run this command" does.

#### Install and adapt [Skills for Real Engineers](https://github.com/mattpocock/skills)

**[Skills for Real Engineers](https://github.com/mattpocock/skills)** is the skill pack this book expects you to open. It is a set of small, editable engineering workflows (grill, spec, tickets, TDD, review, handoff), published so you can change them. The author's install note matters: a plugin updates itself; [skills.sh](https://www.skills.sh/) copies files you edit by hand. Install one path per agent. Installing both gives you every skill twice.

- On Claude Code, Codex, or Copilot, the README's plugin install is the path that updates itself.
- On Cursor, OpenCode, and other agents, `npx skills add mattpocock/skills` copies the files into the project so you can edit them. Include `setup-matt-pocock-skills` when the installer asks, and run that setup once per repo.

Then change the copy. A skill that names a test command you do not have will send the agent into a failing loop. Replace the command with yours. Delete skills you will not use this week. The point of this repository, against the big process packs later in the chapter, is that you can read one file and own it.

#### Grill, spec, tickets, TDD, and code review loops

Use the pack as loops, not as a pile of slash commands. Each loop has a done check.

- **Grill.** `grill-with-docs` and `grilling` interview the design before code. They sharpen terms and can write a glossary or an ADR. Done means you can point at a decision, not at a vibe.
- **Spec.** `to-spec` turns the conversation you already had into a spec on the issue tracker. Done means a teammate could implement it without the chat.
- **Tickets.** `to-tickets` splits that spec into small tickets with blocking edges. Done means each ticket is one diff, not an epic.
- **TDD.** `tdd` writes the failing test first, then the change. Done means the new test failed once and passes after the edit.
- **Code review.** The pack closes implementation with a review pass (`code-review` from `implement`) before the commit. Done means you read the diff, not only the agent's summary.

Run one loop on a real task this week. If you run all of them on a one-line fix, you spent the context window on process. Match the loop to the risk: a glossary change can stop at grill; a behavior change needs the test.

#### [Cursor](https://cursor.com/docs/skills) skills, [Claude Code](https://github.com/anthropics/claude-code) plugins, and the [skills.sh](https://www.skills.sh/) installer

Three ways to get a skill onto the agent:

- **Cursor skills.** Drop the folder in `.cursor/skills/` or `.agents/skills/`. Cursor also reads `.claude/skills/` and `.codex/skills/` for compatibility. Invoke with `/` in Agent chat, or let the description auto-load. Docs: [Agent Skills](https://cursor.com/docs/skills).
- **Claude Code plugins.** A plugin can bundle skills, hooks, and commands and update from a marketplace. That is the right install when you want upstream changes. It is the wrong install when you need to edit the prompt today. Uninstall the plugin before you add a hand-edited copy of the same skills.
- **[skills.sh](https://www.skills.sh/).** The directory and the `npx skills add <owner/repo>` installer. It copies skill folders into the agent you name (`-a cursor`, and the others listed on the site). You own the files. You update them with the installer's update command, then re-read the diff so an upstream skill does not wipe your test command.

After any install, ask the agent to list the skills it can see, and invoke one by name on a tiny task. If it cannot see the skill, the directory is wrong. Fix the path before you rewrite the instructions.

#### [Anthropic skills](https://github.com/anthropics/skills) and other public skill catalogs

**[anthropics/skills](https://github.com/anthropics/skills)** is Anthropic's public catalog (design, documents, a skill-creator, and others). [skills.sh](https://www.skills.sh/) indexes that repo next to `mattpocock/skills` and many more. Treat a catalog like a dependency:

- Read the `SKILL.md` before you install it. The description tells you when it will fire.
- Prefer a skill that tells the agent to run your tests over a skill that only sets a tone.
- Pin the copy in git when the skill changes how code is written. A marketplace skill that updates overnight can change your diffs without a commit you authored.
- One catalog skill this week is enough. A dozen auto-loaded skills crowd the window and fight each other.

The [Agent Skills spec](https://github.com/agentskills/agentskills) is the compatibility check. If a "skill" is a proprietary blob you cannot open, it is not this format, and you cannot review it.

### Agent hooks

A **hook** is a script the agent host runs at a named point in the loop: before a tool, after a tool, at session start, at stop. The model does not choose to follow it. The process runs. [Cursor hooks](https://cursor.com/docs/hooks) live in `.cursor/hooks.json` (project) or `~/.cursor/hooks.json` (you). [Claude Code hooks](https://docs.anthropic.com/en/docs/claude-code/hooks) live in `.claude/settings.json`. Cursor can also load Claude's hook files when third-party imports are on; the event names map (`PreToolUse` to `preToolUse`, and the rest in [third-party hooks](https://cursor.com/docs/reference/third-party-hooks)).

#### [Cursor](https://cursor.com/docs/hooks) hooks and [Claude Code](https://docs.anthropic.com/en/docs/claude-code/hooks) hooks

Start with one hook that you can see fail. A `preToolUse` or `beforeShellExecution` script that rejects a destructive command, or a `postToolUse` script that appends one line to a gitignored log, is enough to prove the wiring. Commit the project hook. Leave personal experiments in the home-directory file so you do not force them on the team.

Hooks speak JSON on stdin and stdout. Exit code 2 blocks on both Cursor and Claude Code, which is why one script can travel. Read the host's doc for the exact event list before you invent an event name. A hook that calls the network or edits the repo is now part of the agent's privilege. Review it like a CI script.

Codex and Copilot have their own hook files (Codex in `config.toml`, Copilot under `.github/hooks/`). Learn them on the week you are on that agent. The idea is the same: a script at a lifecycle point, with allow or deny.

#### When a hook beats a skill

Use a **skill** when the next step is a judgment: how to grill a design, how to split tickets, how to review a diff. The model has to read the situation.

Use a **hook** when the step must happen whether or not the model agrees:

- Block a command you will not allow (`rm -rf`, a push to the default branch, reading a secrets file).
- Run a formatter or a secret scanner after an edit, every time.
- Refuse to stop the session when the test command has not been run.

A skill that says "never commit secrets" is a wish. A hook that fails the tool call is a control. If you only need the wish, skip the hook. Hooks that fire on every keystroke and call a model will burn the week on latency. Keep the script local and cheap.

### Process packs versus small composable skills

A **process pack** installs a methodology: phases, roles, directories, and often its own hooks. A **small skill** is one `SKILL.md` you can delete. Both can be right. They fail in different ways.

#### [Spec Kit](https://github.com/github/spec-kit), [BMAD](https://github.com/bmad-code-org/BMAD-METHOD), and [GSD](https://github.com/gsd-build/get-shit-done): what they own and what they hide

- **[Spec Kit](https://github.com/github/spec-kit)** (the Specify CLI) is GitHub's spec-driven kit: constitution, specify, plan, tasks, implement. It owns the phase order and the template tree. It hides the work inside those templates. When a command fails, you are debugging the kit's layout as well as the feature. Use it when the team has agreed that a spec lands before code, and someone owns upgrades.
- **[BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD)** is a role-based delivery framework: many skills and agent personas, a ticket tree, and handoffs between roles. It owns the cast and the documents they pass. It hides which instruction actually ran, because a session may load a long skill you did not open. Use it when several people share the same agent workflow and will keep the skills in review. Read `AGENTS.md` in that repo before you adopt it; the maintainers themselves tell you that skill text is paid on every run, so length is not free.
- **[GSD](https://github.com/gsd-build/get-shit-done)** (Get Shit Done) is a leaner plan, execute, and verify loop, with its own hooks and session state, aimed at Claude Code and other agents. It owns the map of a chunk of work that does not fit in one session. It hides that map inside its state directory. Use it when one session keeps forgetting the plan, and a handoff file was not enough.

Install a pack in a scratch branch. Run one feature through it. If you cannot find the instruction that caused a bad edit, the pack is hiding too much for this repo. Uninstall it. You can keep the idea (spec before code) as a single skill.

#### When a thin skill beats a full methodology

A thin skill wins when the behavior is one sentence you will enforce this month: "failing test first," "update the handoff file before you stop," "do not edit generated files." You can read it, diff it, and throw it away.

A methodology wins when the team keeps skipping the same three phases and has named an owner for the templates. The cost is upgrade day: upstream changes a prompt and every agent in the company changes with it. Pin it, review the diff, and keep a way to run the repo with the pack turned off.

[Skills for Real Engineers](https://github.com/mattpocock/skills) sits on the thin side on purpose. Start there. Adopt Spec Kit, BMAD, or GSD when a single skill cannot hold the plan, not because a README promised a transformation.

### Make the agent succeed in YOUR repo

The agent is only as good as the repo's instructions, tests, and the note you leave for the next session. A clever skill on a repo with no test command still guesses.

#### [AGENTS.md](https://agents.md/), `CLAUDE.md`, and Cursor rules

**[AGENTS.md](https://agents.md/)** is the cross-agent file at the repo root: how to build, how to test, which directories are off limits, and what done means. Codex, Copilot, Cursor, and others look for it. Put the shared rules here so you are not maintaining three copies.

**`CLAUDE.md`** is Claude Code's file. Keep it short and point at `AGENTS.md` for anything both tools must share. Claude-only notes (a permission you always allow, a plugin you expect) can live here.

**Cursor rules** live in `.cursor/rules`. Use them for editor-specific guidance and for rules that should attach to certain file globs. The long, tool-neutral version stays in `AGENTS.md`.

If the three files disagree, the agent will follow whichever it loaded last. After you edit them, start a fresh session and ask the agent to repeat the test command. That is the smoke test for the rules files.

#### Repo maps, tests, and browser feedback loops

A **repo map** is a short section in `AGENTS.md`: where the server starts, where the tests live, which generated directories to leave alone. Let the agent search for the rest. Pasting the tree into every prompt spends the window you budgeted in the last chapter.

The **test command** is the assertion. Write the exact command in `AGENTS.md`. The agent's loop for a behavior change is: run the test and see it fail, edit, run it and see it pass. If the suite takes ten minutes, document the one focused command for this area. An agent that cannot run tests will tell you it is done because the code looks plausible.

A **browser loop** is the assertion for UI. Unit tests can pass on a screen that is broken. Have the agent open the page, perform the click, and stop on what it sees. The screenshot or the accessibility snapshot is the evidence, the same way the test log is the evidence for an API change. Images, Audio, and Other Modalities returns to screenshots. Here, the rule is: if a human would check the page, the agent session is not done until something opened the page.

#### Handoffs so the next session does not start from zero

A **handoff** is a markdown note at the end of a session: what changed, what is left, which commands failed, and which files the next agent should read first. [Skills for Real Engineers](https://github.com/mattpocock/skills) includes a `handoff` skill that writes one. A dated file in the repo, or a gitignored local note if it contains sensitive paths, works too.

The next session starts by reading that note, not by replaying the chat. Chats are not in git. The handoff is. Date it, and delete it when the work lands, so a stale handoff does not outrank the code the way a stale memory note does.

That is the week: one agent, one skill you edited, one hook if a rule must be mechanical, `AGENTS.md` with the test command, and a handoff the next session can open.

### Summary: Coding Agents and Skills

A coding agent is a model with your files and your shell. Stay on one of [Cursor](https://cursor.com/), [Claude Code](https://github.com/anthropics/claude-code), [Codex](https://github.com/openai/codex), or [GitHub Copilot](https://github.com/features/copilot) for a week, or on [Aider](https://github.com/Aider-AI/aider) or [OpenCode](https://github.com/sst/opencode) if you want the terminal. Leave [Continue](https://github.com/continuedev/continue) to existing installs: Cursor acquired it, and the repo is unmaintained. Change default behavior with a **`SKILL.md`** folder from the [Agent Skills](https://github.com/agentskills/agentskills) format. Install [Skills for Real Engineers](https://github.com/mattpocock/skills) once, edit the test command, and run one loop (grill, spec, tickets, TDD, or review). Use [skills.sh](https://www.skills.sh/) or a plugin, not both. Enforce mechanical rules with [Cursor hooks](https://cursor.com/docs/hooks) or [Claude Code hooks](https://docs.anthropic.com/en/docs/claude-code/hooks). Adopt [Spec Kit](https://github.com/github/spec-kit), [BMAD](https://github.com/bmad-code-org/BMAD-METHOD), or [GSD](https://github.com/gsd-build/get-shit-done) only when a thin skill cannot hold the plan. Put the shared rules in [AGENTS.md](https://agents.md/), keep the test command true, check the UI in a browser when a human would, and leave a handoff. ## Structured Outputs and Tool Calling

The last chapter's agent is done when a test passes. This chapter is done when a program can trust the object's fields. A JSON prompt from Prompting, Context, and System Instructions asks the model to behave. **Structured output** makes the shape part of the call. **Tool calling** is the other shape: the model names a function and arguments, and your code runs the function.

Keep the smoke test. Change the assertion from "the text contains a label" to "this object validates, or the run fails." If the model returns a paragraph, the run fails. You do not scrape the paragraph.

### JSON you can trust

JSON you can trust has three properties: every required field is present, each field has the type you declared, and a value from a closed set is one of those values. Pretty-printed JSON that is missing `severity` is a failed call. So is `"severity": "kinda high"` when the schema says `low` or `high`.

Define the schema in code you review, next to the fixture. A three-field object is enough for the first green run: a label enum, a short string, and an optional note. Grow the schema when a real record needs another column, not before.

#### Native structured outputs from hosted APIs

Use the provider's structured-output mode before you add a library. It constrains the reply to a JSON Schema. JSON mode only promises that the text parses as JSON. Structured output promises the schema.

- **[OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs).** Structured Outputs on the Responses API (`text_format` with a Pydantic model or a Zod object in the SDKs, or a `json_schema` response format). Strict mode requires you to mark properties required and set `additionalProperties` to false. The same guide separates this from function calling: structured text is the answer to the user; a function call is a request that your app do something. Refusals come back as a field you can branch on. A model that only has JSON mode is the older path. Stay on a model id whose docs list structured outputs, and record that id in the smoke test.
- **[Anthropic](https://platform.claude.com/docs/en/build-with-claude/structured-outputs).** JSON outputs via `output_config.format`, and `messages.parse` in the Python SDK when you pass a Pydantic model. Strict tool use is the matching guarantee on tool arguments. You can use either feature, or both: the tool call is how Claude acts, the JSON output is what Claude says at the end.
- **[Gemini](https://ai.google.dev/gemini-api/docs/structured-output).** A response schema, with Pydantic or Zod in the GenAI SDKs. Gemini's own split matches the others: structured output formats the final answer; [function calling](https://ai.google.dev/gemini-api/docs/generate-content/function-calling) is the action in the middle. Combining them is documented for Gemini 3 models. Confirm the model id you smoke-test is one of those if you need both in one request.

Point the same fixture at the host you already pay for. Assert the parsed object. Then send a fixture that cannot fit the enum and assert that you record a refusal or a validation failure. A green test that accepts any string has not tested the schema.

Local servers are behind on this. [Ollama](https://docs.ollama.com/api/openai-compatibility)'s compatible API has JSON mode and tools, and it does not implement every strict-schema flag. [llama.cpp](https://github.com/ggml-org/llama.cpp)'s server can constrain with a grammar. If the laptop model cannot hold the schema, keep the schema and run that fixture against the hosted model. Do not weaken the assertion so the local model looks green.

#### [Instructor](https://github.com/567-labs/instructor) and Pydantic for validated objects

**[Instructor](https://python.useinstructor.com/)** ([repo](https://github.com/567-labs/instructor)) wraps a provider client and returns a [Pydantic](https://docs.pydantic.dev/) model. You pass `response_model`. Instructor asks the provider for structure, validates, and on failure sends the validation error back and retries. Python, TypeScript, and other language ports exist. One call site can target OpenAI, Anthropic, Gemini, and an OpenAI-compatible local server.

Use it when you want the retry loop written down once, and when the schema is a Pydantic class you already use for the rest of the app. The smoke test is the class: construct nothing by hand from a string. If `User(name=..., age=...)` would reject the payload, the call rejects it.

Native structured outputs and Instructor overlap. Prefer the native mode on a host that already guarantees the schema, and keep Pydantic as the type you validate into. Add Instructor when you need the same model across two providers, or when a provider's JSON mode still needs a retry. Do not stack three parsers. One schema, one validation step, one place that logs the raw payload on failure.

#### [Outlines](https://github.com/dottxt-ai/outlines) and [BAML](https://github.com/boundaryml/baml) for constrained generation

**[Outlines](https://dottxt-ai.github.io/outlines/latest/)** constrains generation to a schema, a regex, or a grammar. On a runtime that exposes logits ([vLLM](https://github.com/vllm-project/vllm), [llama.cpp](https://github.com/ggml-org/llama.cpp), Transformers), invalid tokens are masked, so the decode cannot wander into prose. That is the point of running your own server. Outlines also speaks to hosted APIs; the token-level guarantee is the self-hosted path. Reach for it when you already serve a model and a retry loop is how you pay for bad JSON.

**[BAML](https://docs.boundaryml.com/)** ([repo](https://github.com/boundaryml/baml)) moves the prompt and the types into `.baml` files. The compiler generates a client. You version the contract, you test it, and a tolerant parser accepts some of the messy JSON models actually emit (trailing commas, a missing close) without accepting a different schema. Reach for BAML when several services call the same extraction and you want the prompt in review next to the types, the way you review an API spec.

Pick one constraint tool for the repo. Native structured outputs or Instructor cover a hosted extraction. Outlines covers a GPU box. BAML covers a contract you will generate clients from. A second library is a second place for the schema to drift.

### Function calling and tools

A **tool** is a function the model may ask your application to run. The model returns a name and arguments. Your process runs the function, or refuses it. You send the result back. The model continues. The model does not have your database password, and it does not execute the shell unless you wrote a tool that does.

That loop is the same one a coding agent hides. Here you own it, so you can test it.

#### [OpenAI](https://developers.openai.com/api/docs/guides/function-calling) tools, [Anthropic](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) tool use, and [Gemini](https://ai.google.dev/gemini-api/docs/generate-content/function-calling) function calling

Declare each tool with a name, a description that says when to use it, and a JSON Schema for the arguments. Turn on strict or structured arguments where the host offers them, so a missing required argument fails before your function runs.

- **[OpenAI](https://developers.openai.com/api/docs/guides/function-calling).** Tools on the Responses API or Chat Completions. The flow is: send the tools, receive a call, run your code, send the tool output, receive the next message or another call. `strict: true` applies structured outputs to the arguments. Keep the tool list small. A later note in the same guide, tool search, exists for large catalogs. You do not need it for two functions.
- **[Anthropic](https://platform.claude.com/docs/en/build-with-claude/structured-outputs).** Tool use, with strict tool use when you need the arguments to match the schema. The tool result goes back on the next user turn as a tool result block. Copy that shape from the docs. An OpenAI-shaped message list will not do.
- **[Gemini](https://ai.google.dev/gemini-api/docs/generate-content/function-calling).** Function declarations. The model returns a call. Your code runs it. You return a function response. Gemini 3 returns an id on the call so parallel calls stay matched. The model still does not run the function.

The smoke test for a tool is a stub. Register one function, `echo_label`, that returns the label it was given. Assert that the model called that name, that the arguments validate, and that your stub's return value appears in the following request. A test that only checks the final prose can pass while the tool never ran.

Allowlist the names. If the model asks for a tool you did not register, fail the turn and log the name. Model Context Protocol (MCP), later in the book, is how you publish a set of tools to many clients. This chapter is one process and one list.

#### [PydanticAI](https://github.com/pydantic/pydantic-ai) for typed Python agents

**[PydanticAI](https://ai.pydantic.dev/)** is the agent runtime from the Pydantic team: a result type, tools as typed functions, and a loop that stops when the result validates. [Instructor](https://github.com/567-labs/instructor)'s own docs draw the line: Instructor for a single extraction, PydanticAI when the job is an agent with tools, retries, and a typed final answer.

Use PydanticAI when you are writing the loop yourself in Python and you want the tool arguments and the final object to be the same kind of model. Skip it when the coding agent from the previous chapter already is the loop, or when one structured call fills the record. An agent framework around a single extraction hides the one request you should be able to log.

The smoke test is unchanged: a fixture, a stub tool, a result object that validates, and a raw log of each tool call. If you cannot see the call in the log, the types are decorative.

#### Retries, validation errors, and refusing to parse prose

Cap retries. Two or three attempts is a policy. Each retry includes the validator's message ("`severity` must be `low` or `high`, got `urgent`"), not a new essay from you. Log the raw model text, the schema name, the model id, and the attempt number.

Stop when the cap is hit. Mark the job failed. Leave the record empty. A human or a queue can look at the log. Filling the spreadsheet with a regex over the paragraph trains the team to trust a path you cannot test.

Refuse these shortcuts:

- A parser that finds the first `{` and the last `}` and hopes.
- `try/except` that stores the whole reply in a `notes` column and continues.
- A prompt line that says "really return JSON" after structured outputs are available on that host.

JSON mode plus a retry is legitimate on a model with no schema mode. Say so in the test name, so nobody thinks the enum is guaranteed. When you move that call to structured outputs, delete the prose parser in the same commit.

### When a spreadsheet or form is the real interface

Many products do not need a chat box. The user lives in a sheet, a form, or a queue of tickets. The model is a function from messy text to a row. Ship that function. Add a chat when a person still has to ask a follow-up the row cannot hold.

#### Extract, classify, and fill records from messy text

One schema can do the three jobs, and the smoke test should separate them:

- **Extract.** Pull the fields that are in the text: a name, a date, an amount. If the amount is absent, the field is null. Guessing an amount is a failed fixture. Put that fixture in the suite.
- **Classify.** Pick one label from the enum. The description on the schema says what each label means. An input that fits two labels is a schema bug or a fixture that should land on the label you wrote down. Update the enum or the fixture. Do not let the model invent `other_other`.
- **Fill.** Write the object into the row, the form, or the ticket fields your app already has. The write happens in your code after validation. The model never receives the production credentials. A dry-run mode prints the row and writes nothing, and the smoke test uses the dry run.

Keep the source text beside the row in a place a reviewer can open, or store an id that points back to it. When the row is wrong, you need the text that produced it. That pair, source plus validated object, is also the start of the golden set in Evaluation, Tracing, and Guardrails.

Run the suite when you change the schema, the prompt file, or the model id. One fixture for the happy path, one for a missing field, one for a label that must not be guessed. Three rows beat a demo transcript.

### Summary: Structured Outputs and Tool Calling

Trust a model when the reply validates against a schema you store next to the test. Use native structured outputs on [OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs), [Anthropic](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), and [Gemini](https://ai.google.dev/gemini-api/docs/structured-output) for the answer shape, and their tool or function-calling APIs when your code must act. [Instructor](https://github.com/567-labs/instructor) retries a Pydantic model across providers. [Outlines](https://github.com/dottxt-ai/outlines) constrains decoding on a server you run. [BAML](https://github.com/boundaryml/baml) turns the prompt and the types into a generated client. [PydanticAI](https://github.com/pydantic/pydantic-ai) is the typed loop when there is more than one tool call. Cap retries, log the raw payload, and leave the record empty when validation fails. If the real interface is a sheet or a form, extract, classify, and fill that row. Next is **Retrieval-Augmented Generation (RAG)**, where the text you extract from is a document you retrieved, not a paragraph pasted into the prompt.

## Retrieval-Augmented Generation (RAG)

The structured call in the last chapter can only extract what you put in the prompt. **Retrieval-Augmented Generation (RAG)** fetches a few passages from documents you already have, puts those passages in the prompt, and asks the model to answer from them. The model is still a generator. The index is what keeps it on your files.

The smoke test changes. Before you grade the prose, print the passages you retrieved. If the right paragraph is missing, the answer will be a guess, and editing the prompt will not put the paragraph back.

### The working RAG loop

Five steps, in this order, on a corpus you can open in a file browser:

1. **Ingest.** Turn files or pages into text, and keep the source path, page, and heading on each piece.
2. **Chunk.** Split that text into pieces small enough to embed and large enough to answer a question.
3. **Embed.** Turn each chunk into a vector with one recorded embedding model.
4. **Retrieve.** Given a question, return the top chunks, plus any keyword matches you asked for.
5. **Generate.** Call the model with the question, those chunks, and a contract: answer from the chunks, and name the source. If the chunks do not contain the answer, say so.

Run steps 1–4 until the right chunk is in the list. Only then spend a generation. Log the embedding model id the way you log the chat model id. Vectors from two embedding models do not belong in the same index.

#### Ingest, chunk, embed, retrieve, generate

Start with a folder of documents you would be willing to show a colleague, and five questions whose answers you can point at with a finger. Write the expected source next to each question: file, page or heading, and a short quote. That list is the retrieval test. It is not a prompt.

**Chunk** on structure when the file has it: headings, slides, pages, rows. A fixed token window is the fallback, with a small overlap so a sentence cut in half still appears in one piece. Store metadata on every chunk: source, page, heading, and a date if the file has one. A later filter on "only the 2024 handbook" is metadata. It is not a smarter paragraph.

**Embed** with one model and write its name into the index config. Hosted embedding APIs (the same accounts as the first working loop) are fine for a first index. A local embedding model belongs here when the documents cannot leave the machine. Re-embed the corpus when you change the model. Do not append new vectors from a second model into an old index.

**Retrieve** a small k, often 4 to 8, and print them. **Generate** with the system prompt from the prompting chapter: the chunks are evidence, the question is the task, and the output contract includes a citation (file and page, or the chunk id). Use the structured-output schema when the product needs a row plus a list of sources. The citation has to match a chunk you actually passed in. A fabricated filename fails the test.

Change one thing and rerun the five questions: chunk size, metadata, k, or the embedding model. The prompt stays put until retrieval is boringly right.

#### When RAG is the wrong fix

RAG is a search problem with a generator on the end. Reach for something else when there is no corpus, or when the corpus is not where the answer lives.

- The fact is already in the user message, or it is a format you can show with a prompt and a schema. That is Prompting, and Structured Outputs.
- The answer is a calculation, a ticket update, or a test run. That is a tool, not a paragraph.
- The task is a change in a repository. That is a coding agent with search over the tree, which is a form of retrieval, and it still needs the test command from Coding Agents and Skills.
- The question needs a relationship across the whole set ("how do these teams depend on each other"), and every single paragraph is locally true and globally useless. Microsoft GraphRAG, later in this chapter, is the tool to try before you paste the corpus into the window.
- You hope a fine-tune will memorize the handbook. Shipping, Cost, and Operations keeps adapters for the case where retrieval already returns the right text and the model still will not follow it. Retrieval comes first.

If you cannot name the file that should have answered question three, you do not have a RAG project yet. You have a writing project.

### Ingest documents you actually have

The index is only as good as the text you extracted. A PDF full of headers, footers, and a table read as a single line will retrieve garbage with a perfect embedding model. Look at three extracted pages before you embed the folder.

#### [Unstructured](https://github.com/Unstructured-IO/unstructured) and [Docling](https://github.com/docling-project/docling) for PDFs and office files

**[Unstructured](https://github.com/Unstructured-IO/unstructured)** ([docs](https://docs.unstructured.io/)) partitions PDFs, Office files, and HTML into elements: titles, narrative text, tables, lists. Use it when the folder is mixed and you want one partition step with metadata you can filter on. Read the elements for one file. If the table you care about became a blob of numbers, fix the partition before you chunk.

**[Docling](https://github.com/docling-project/docling)** ([docs](https://docling-project.github.io/docling/)) parses PDF, DOCX, PPTX, and HTML into a layout-aware document, including tables. Use it when the documents are real reports and the answer is often in a table or a section, not in a paragraph of prose. Docling's own technical report is a fine first file to parse so you can see the structure on something public.

Pick one parser for the folder. Run it on the five source files from your question list. Diff the extracted text against the page. Then chunk. A second parser is justified when the first one drops the table you needed for question two.

#### [Firecrawl](https://github.com/mendableai/firecrawl) and [Crawl4AI](https://github.com/unclecode/crawl4ai) for websites

**[Firecrawl](https://docs.firecrawl.dev/)** ([repo](https://github.com/mendableai/firecrawl)) turns a site into markdown or structured extracts through an API: scrape, crawl, and map. Use it when the corpus is a public or authenticated site and you want a hosted crawl with a key, the same way you use a hosted chat model. Respect the site's terms and robots rules. Store the URL and the fetch time on each page. A page you crawled last quarter is a stale chunk, and the model will cite it with confidence.

**[Crawl4AI](https://github.com/unclecode/crawl4ai)** is the open-source crawler you run yourself. It drives a browser and emits markdown aimed at a model. Use it when the pages are yours, when you cannot send them to a crawl API, or when you need the crawl in the same repo as the index job.

Crawl a path, not the internet. A seed URL, a depth or a sitemap, and a list of domains you allow. Write the pages to disk first, then run the same chunk and embed steps you used for PDFs. The retrieval test does not care that the source was HTML. It cares that question four's quote is in a chunk.

### Indexes and vector stores

An index is the thing you query. A framework is how you load, chunk, and call the model. A vector store is where the vectors and the metadata sit. You can outgrow a framework and keep the store, or the reverse. Write down which is which before you install three of them.

For this week, one framework and one store. The five questions stay the test.

#### [LlamaIndex](https://github.com/run-llama/llama_index) as a data framework

**[LlamaIndex](https://developers.llamaindex.ai/)** ([repo](https://github.com/run-llama/llama_index)) is built around the index: load documents, chunk, embed, retrieve, synthesize. Start here when the product is "ask questions of this folder" and you want that loop with the fewest new nouns. Use a reader that matches the parser you already chose, including Docling if that is what produced clean text.

Keep the index build as a script you can rerun. Persist the index to a directory you can delete. If the only copy lives in a notebook you cannot find, you do not have a loop. After a rebuild, rerun the five questions and compare which chunk ids came back.

#### [LangChain](https://github.com/langchain-ai/langchain) retrievers and loaders

**[LangChain](https://docs.langchain.com/)** ([repo](https://github.com/langchain-ai/langchain)) is a box of loaders and retrievers. Use it when you already have LangChain in the app, or when the source is one of its loaders (Docling, Unstructured, Firecrawl, a drive, a database) and you want a `Document` with metadata in a shape the rest of the stack expects. A retriever is the object that hides "embed the question, query the store, return documents." Log the documents. A chain that only returns the final answer has skipped the only step that tells you whether search worked.

LangChain and LlamaIndex solve the same week. Installing both to compare their tutorials will split your schema. Pick the one whose loader already reads your files.

#### [Haystack](https://github.com/deepset-ai/haystack) pipelines

**[Haystack](https://docs.haystack.deepset.ai/)** ([repo](https://github.com/deepset-ai/haystack)) is an explicit pipeline: components for converting, embedding, retrieving, and generating, wired in order. Use it when you want to see each stage as a node you can swap, and when you would rather debug a pipeline graph than a hidden chain. The integrations cover the same neighbors: Docling, Unstructured, Firecrawl, and the vector stores below.

A Haystack pipeline earns its place when two people will edit the stages. For a solo smoke test, the extra graph is optional. The five questions are not.

#### [Chroma](https://github.com/chroma-core/chroma), [Qdrant](https://github.com/qdrant/qdrant), [Weaviate](https://github.com/weaviate/weaviate), and [Milvus](https://github.com/milvus-io/milvus)

The store holds vectors, the text, and the metadata. Filter on metadata in the query. A vector-only search over a mixed corpus will retrieve a chunk from the wrong year that happens to share words.

- **[Chroma](https://docs.trychroma.com/)** ([repo](https://github.com/chroma-core/chroma)). Embedded, on the laptop, one directory. The right first store for the five-question test. You can move the same chunks later.
- **[Qdrant](https://qdrant.tech/documentation/)** ([repo](https://github.com/qdrant/qdrant)). Local or a server, with payload filters. Move here when you need a process that stays up and filters that Chroma's toy collection is getting awkward.
- **[Weaviate](https://weaviate.io/developers/weaviate)** ([repo](https://github.com/weaviate/weaviate)). Hybrid search is a first-class query: vectors and keywords together. Useful when exact tokens (error codes, SKUs, names) matter as much as paraphrases.
- **[Milvus](https://milvus.io/docs)** ([repo](https://github.com/milvus-io/milvus)). The scale-out store. Use it when the corpus or the query rate has left a single node, not on the afternoon you are still fixing chunk boundaries.

Whatever you pick, record the collection name, the embedding model, and the distance metric. A rebuild that silently changes any of those is a different index. Rerun the five questions after every rebuild.

### Search that does not embarrass you

Embarrassing search returns a chunk that shares vocabulary with the question and misses the passage that answers it. You notice only if you print the chunks. The fixes are mechanical: keywords plus vectors, a rerank step, citations the user can check, and a score on the retrieval test before anyone touches the prompt.

#### Hybrid search, rerankers, and citations

**Hybrid search** runs a keyword query (BM25 or the store's sparse index) and a vector query, then merges the lists. Exact strings survive the keyword side. Paraphrases survive the vector side. Weaviate and several of the other stores can do this in one query. If your store cannot, run both and merge by hand for the smoke test so you can see the gain on the five questions. Question wording that is an error code or a proper noun is the case that usually moves.

A **reranker** is a second model that reads the question plus each candidate chunk and reorders them. It is slower than the first retrieval and it is worth it when the right chunk is in the top 20 and not in the top 4. Keep the first-pass k larger, rerank down to the chunks you will actually put in the prompt, and log both lists. If the right chunk never enters the first list, a reranker cannot invent it. Fix the chunking or the index.

**Citations** are part of the contract, not a footnote you hope for. The generator may only name sources you passed in. The app should render the file and the page, and the test should fail when the named source is not in the retrieved set. A fluent answer with no citation is an unscored answer. Show the passage under the citation so a reader can disagree with the model without opening the corpus.

#### [Microsoft GraphRAG](https://github.com/microsoft/graphrag) when relationships matter

**[GraphRAG](https://github.com/microsoft/graphrag)** builds an entity graph from the corpus and summarizes communities of that graph, then retrieves those summaries as well as local text. Use it when the questions are about connections: who reports to whom, which services depend on which config, what changed across a set of incident reports. A vector index will happily return one accurate paragraph about one team and miss the edge between teams.

It costs an extraction pass over the corpus, with a model in the loop, before anyone asks a question. Run it on a subset you already understand. Ask a relationship question your five-question list was failing, and compare the retrieved summary to the vector index's top chunks. If the graph summary answers it and the chunks did not, keep GraphRAG for that class of question. If both miss it, the fact is not in the documents. No index will add it.

Do not start on GraphRAG. Start on chunks. Add the graph when you can show a question the chunks cannot answer and the relationships can.

#### Evaluating retrieval before you tune the prompt

Score retrieval on the five questions, then on a larger set when the five are green. For each question, record whether the expected quote appeared in the retrieved chunks, at what rank, and which file came back instead. That is a pass/fail you can put in the same smoke test as the schema checks.

Change the index when the quote is absent. Change k or add a reranker when the quote is present but buried. Change the prompt only when the quote is in the prompt and the answer still ignores it, cites the wrong chunk, or adds a fact that is not in the text. The last case is a contract failure. The structured-output schema can require a list of chunk ids, and the test can reject ids you did not retrieve.

Evaluation, Tracing, and Guardrails will name [Ragas](https://github.com/explodinggradients/ragas) and [DeepEval](https://github.com/confident-ai/deepeval) for the fuller checks. You do not need those libraries to refuse a prompt edit while question two still retrieves the wrong page. A spreadsheet with five rows and a yes/no column is the whole harness until the corpus grows.

When the five questions retrieve the right pages twice in a row after a rebuild, the loop is real. The next chapter puts that retrieve step inside an agent that can decide to search, call a tool, and stop.

### Summary: Retrieval-Augmented Generation (RAG)

RAG is ingest, chunk, embed, retrieve, and only then generate, tested by whether the right passage came back. Parse real files with [Unstructured](https://github.com/Unstructured-IO/unstructured) or [Docling](https://github.com/docling-project/docling), and real sites with [Firecrawl](https://github.com/mendableai/firecrawl) or [Crawl4AI](https://github.com/unclecode/crawl4ai). Build the loop in [LlamaIndex](https://github.com/run-llama/llama_index), [LangChain](https://github.com/langchain-ai/langchain), or [Haystack](https://github.com/deepset-ai/haystack), and store vectors in [Chroma](https://github.com/chroma-core/chroma) until you need [Qdrant](https://github.com/qdrant/qdrant), [Weaviate](https://github.com/weaviate/weaviate), or [Milvus](https://github.com/milvus-io/milvus). Add hybrid search, a reranker, and citations so a wrong paragraph is visible. Use [GraphRAG](https://github.com/microsoft/graphrag) when the question is about relationships the best paragraph cannot hold. Score retrieval before you edit the prompt. Next is **Agents and Multi-Step Workflows**, where retrieval is one tool in a loop that can plan, act, and stop.

## Agents and Multi-Step Workflows

A coding agent edits a repo. A RAG call answers from passages. This chapter is the loop you write when the product has to do more than one of those: search, call a tool, read the result, and either stop or take another step. The personality in the system prompt does not make it an agent. The loop does.

Pick one framework for the week. Give it two tools you already trust: the retrieval function from the last chapter, and one stub that returns a fixed value. The smoke test is a trace of plan, action, observation, and stop, with a step cap that actually fires.

### An agent is a loop with tools, not a personality

An **agent** is your code around a model. Each turn, the model may reply with a final answer or with a tool call. You run the tool, or you refuse it, and you append the observation. Then you call the model again. Structured Outputs and Tool Calling already defined that contract for one call. Here the contract repeats until a stop condition.

Write the stop conditions down before you admire a demo:

- A validated result object, from the schema you already test.
- A step cap, small enough that a stuck loop dies in front of you. Ten steps is plenty for the first fixture.
- A tool error you do not understand. Stop and log it. Do not ask the model to "try something else" forever.
- A human gate on any action that leaves the machine: send, pay, delete, push, or write to a system of record.

If the trace does not show which tool ran and what it returned, you have a chat with extra latency. Log every step: the tool name, the arguments, the observation, and the reason you stopped.

#### Plan, act, observe, stop

Four words are the whole loop. Keep them visible in the trace.

- **Plan.** One next action, not a essay. A graph node, a handoff, or a single sentence the log can store. If you cannot name the next tool, the agent is not ready to act.
- **Act.** One tool call. Your process executes it. The model does not hold the credentials, and it does not get a second tool in the same breath until the first observation is back.
- **Observe.** Store the tool result, not the model's paraphrase of it. The next turn sees the raw payload, trimmed if it is huge, with the source id when the tool was retrieval.
- **Stop.** Hit a condition above and end the run. A final answer that skips the observation is a failed fixture, even if the prose sounds right.

The first fixture is boring on purpose. Question in, retrieval tool returns a canned passage, answer must cite that passage, and a third step is a failure. When that trace is stable, add a second tool. The coding-agent week already taught you what happens when the loop can edit files. This loop should earn that power one tool at a time.

#### Human approval gates you should not skip

A **human approval gate** pauses the loop and waits for a person before a side effect. Put the gate in the framework's interrupt or suspend, not in a sentence in the prompt that says "ask me first." The prompt is a wish. The pause is a control, the same distinction as a hook versus a skill.

Gate at least these:

- Anything a customer will see sent.
- Anything that moves money, deletes a row, or merges to the default branch.
- The first time a new tool is allowed to run outside a stub.

Show the person the tool name, the arguments, and the observation so far. Approve, edit the arguments, or stop. A checkpoint that can resume after the approval is the point of a stateful framework. A loop that restarts from zero after every "yes" will burn the window and the patience.

While you are still on stubs, the gate can be a test that fails if the dangerous tool is called without an approval flag. Wire the real pause when the tool becomes real.

### Frameworks you can ship with

Six frameworks cover the shapes teams actually ship. Install one. The others are the map for the day a requirement shows up: resume tomorrow, a TypeScript app, a role-shaped crew, a code-writing agent, or a Microsoft stack that used to be AutoGen.

The smoke test does not change with the logo. Same fixture, same two tools, same step cap, same trace.

#### [LangGraph](https://github.com/langchain-ai/langgraph) for stateful graphs and checkpoints

**[LangGraph](https://github.com/langchain-ai/langgraph)** is a graph. Nodes are steps, edges are decisions, and a checkpointer stores the state so a run can pause and resume. Use it when the workflow must survive a restart, a human approval, or a retry of one node without replaying the whole chat. LangChain can sit underneath for model calls and retrievers. You do not have to adopt every LangChain abstraction to use the graph.

Draw the graph on paper first: retrieve, answer, or ask a human. Then implement those nodes. A checkpoint you cannot reload is only a log. After the smoke test passes, kill the process on purpose and resume from the checkpoint. That is the feature you picked LangGraph for.

#### [OpenAI Agents SDK](https://github.com/openai/openai-agents-python)

The **[OpenAI Agents SDK](https://github.com/openai/openai-agents-python)** ([guide](https://developers.openai.com/api/docs/guides/agents)) is a library that runs in your process: an agent with instructions and tools, handoffs to other agents, and a runner that loops until the agent stops. There is a TypeScript SDK as well. Tracing is part of the run, which is what you want when the smoke test is a trace.

OpenAI also offers a hosted Agents API, where they run the harness. That is a different deployment. This section is the SDK, because you can see the tool execute in your code and you can point the same patterns at another model later. Use the SDK when you want the smallest agent loop that still has handoffs and a session, and you are already on the OpenAI client from the first chapters. Keep the tools you register on an allowlist. A handoff to a second agent is a second place to log, not a reason to skip the step cap.

#### [CrewAI](https://github.com/crewAIInc/crewAI) crews and flows

**[CrewAI](https://github.com/crewAIInc/crewAI)** ([docs](https://docs.crewai.com/)) splits the work into **crews** and **flows**. A crew is a set of role-shaped agents that share a task. A flow is the event-driven path around them: branches, state, and the places you refuse to leave to a role-play. Use a crew when the work really is two jobs with two instructions, such as "retrieve" and "check the citations." Use a flow when the order must hold even if an agent is enthusiastic.

A crew with five personalities and one tool is a prompt you split for theater. Start with one agent and one flow. Add a second role when the trace shows a step you want isolated, and give that role its own done check. If you cannot tell which role wrote a bad line, you added roles too early.

#### [Microsoft Agent Framework](https://github.com/microsoft/agent-framework) after AutoGen

**[Microsoft Agent Framework](https://learn.microsoft.com/en-us/agent-framework/)** ([repo](https://github.com/microsoft/agent-framework)) is the framework Microsoft wants for new agent work, in Python and .NET. It carries the multi-agent patterns people used **[AutoGen](https://github.com/microsoft/autogen)** for, plus workflow graphs, checkpoints, and human-in-the-loop steps. AutoGen remains for existing apps. Its own direction is maintenance, not a stream of new features. A new service goes to Agent Framework, with the migration notes Microsoft publishes, rather than a fresh AutoGen project you will have to move.

Pick it when the team is already on Azure or .NET, or when you are leaving AutoGen and want the supported successor. The smoke test is still your two tools and a checkpoint you can resume. A sample that only chats between two agents has not proved the framework.

#### [Hugging Face smolagents](https://github.com/huggingface/smolagents)

**[smolagents](https://github.com/huggingface/smolagents)** is a small library whose distinctive agent writes actions as Python code, then runs that code, instead of only emitting a JSON tool call. A tool-calling agent is also in the box if you want the JSON shape you already tested. Use smolagents when the next step is easier as a few lines of code than as another tool schema, and when you can run that code in a sandbox. A code agent on your laptop with your credentials is a shell with a model in front of it.

Point it at the model you already smoke-test, including a local OpenAI-compatible server. Assert that the code it ran is in the trace, and that the sandbox, not your home directory, was the working directory. If you cannot show the code, you cannot review it.

#### [Mastra](https://github.com/mastra-ai/mastra) as a TypeScript agent framework

**[Mastra](https://mastra.ai/)** ([repo](https://github.com/mastra-ai/mastra)) is the TypeScript framework in this list: agents, tools, workflows with suspend and resume, and a place for memory and evals next to a Node or React app. Use it when the product is already TypeScript and you do not want a Python service beside it just to hold the loop. Workflows can branch and run steps in parallel. Suspend is the human gate.

The smoke test is a TypeScript test that runs the workflow on the canned retrieval tool and asserts the trace. If the only way to see success is a chat window in the dev server, you have not automated the loop yet.

### Browser, computer, and workflow agents

Some tools are not functions in your repo. They are a browser, a desktop, or a canvas another person will edit. They are still the same loop. The observation is a page, a screenshot, or a node that ran. The step cap still applies. A browser agent that may click anything on the internet is not a first fixture.

#### [Playwright](https://playwright.dev/)-based browsing and [Stagehand](https://github.com/browserbase/stagehand)

**[Playwright](https://playwright.dev/)** drives a real browser: open a URL, click, type, and read the page. Use it when you know the selectors and the flow is stable. The assertion is the same one from Coding Agents and Skills: the page shows the change, or the accessibility snapshot contains the text you expected.

**[Stagehand](https://github.com/browserbase/stagehand)** sits on that browser and lets a model act and extract when the selector is the fragile part. Use it when the page changes often enough that a hard-coded click breaks every week, and you can still check the result without the model. Give it one origin. Log the actions. A step cap of a handful of actions beats a model that "explores." If a Playwright script can do the task, prefer the script. The model is for the step you cannot name in advance.

#### [n8n](https://github.com/n8n-io/n8n), [Dify](https://github.com/langgenius/dify), [Flowise](https://github.com/FlowiseAI/Flowise), and [Langflow](https://github.com/langflow-ai/langflow) when you want a canvas

A canvas is a way to see the loop. It is not a different loop.

- **[n8n](https://github.com/n8n-io/n8n)** is a workflow product: triggers, branches, and HTTP or app nodes, with a model node where you need one. Use it when the agent is one step in a business process that already has triggers and credentials in n8n.
- **[Dify](https://github.com/langgenius/dify)** is an app builder for model workflows, retrieval, and agents, with a UI your team can edit. Use it when the operator is not going to live in a Python file.
- **[Flowise](https://github.com/FlowiseAI/Flowise)** and **[Langflow](https://github.com/langflow-ai/langflow)** are open canvases aimed at LangChain-style graphs. Use one when you want to drag the retrieve-then-generate path and still export something you can run.

Pick a canvas when two people must see the path. Keep the five-question retrieval fixture, or the two-tool agent fixture, as a run you can repeat after someone moves a node. A screenshot of the canvas is not the test. The run's output is the test. Secrets stay in the product's credential store, not in a node you commit.

### Memory engineering

Memory is what the next turn, or the next session, is allowed to see. It is not a transcript you hope the model will skim. The prompting chapter already said a summary is a cache with an expiry. RAG already said documents live in an index. This section is the policy between them: what the agent stores about the work, what it drops, and what it fetches when a new session starts.

#### What to store, what to forget, and what to retrieve

**Store** decisions, stable preferences, and the outcome of an expensive tool call you will reuse: "the customer id is 14," "we chose Qdrant," "the last successful query returned these three chunk ids." Write them as short records with a date and a source.

**Forget** secrets, raw tickets you are not allowed to retain, and any fact a newer observation contradicted. Delete the old record. Do not leave both "the API is v1" and "the API is v2" for the model to average. Forget the full tool payload when you have stored the id and can retrieve the payload again.

**Retrieve** at the start of a step that needs the fact, the way you retrieve a passage. A memory note dumped into every turn spends the window and goes stale in public. The handoff file from Coding Agents and Skills is a memory record a human can read. An automatic store should be at least that legible.

If a memory and a retrieved document disagree, prefer the document for facts about the world and the newer dated memory for facts about this user's choices. Say which one you used in the trace.

#### Working memory versus long-term memory

**Working memory** is this run: the plan, the tool results, the draft answer, the steps remaining. It lives in the graph state or the session. It can be large, and it dies or gets checkpointed with the run. Trim it when the window fills, the way you trim chat history, and do not trim the system rules or the latest observation.

**Long-term memory** is what you keep after the run ends. It is small. It is dated. It is queried, not pasted. A checkpoint is working memory you can resume. It is not long-term memory, and you should not search old checkpoints as if they were a knowledge base. That job is the RAG index.

The bug to avoid is writing every utterance into long-term memory. The store fills with chatter, retrieval returns chatter, and the agent cites a joke from last Tuesday as policy. Write on purpose, at the end of a run, from a schema: a handful of fields, validated like any other structured output.

#### [Mem0](https://github.com/mem0ai/mem0), [Letta](https://github.com/letta-ai/letta), and [Graphiti](https://github.com/getzep/graphiti) as starting points

You can ship the policy with a table and a date column. Reach for a library when you are about to invent that table badly.

- **[Mem0](https://github.com/mem0ai/mem0)** stores and searches memories across a user or a session, and it will extract memories from a conversation. Use it when you want that extraction without designing the schema on day one. Still review what it wrote. An extractor will store a secret if the secret was in the chat and you did not forbid the field.
- **[Letta](https://github.com/letta-ai/letta)** is an agent runtime whose point is memory: the agent edits its own memory blocks inside a context budget. Use it when the experiment is "what should stay in context," not when you already have a graph you like. Read the blocks after a run. If they grew without a decision, tighten the instructions or the tool that writes them.
- **[Graphiti](https://github.com/getzep/graphiti)** builds a temporal knowledge graph of entities and facts that change over time. Use it when long-term memory is relationships with history ("this id used to map to that team"), which a flat list of notes will scramble. It is closer to GraphRAG than to a sticky note. Run it on facts you already store, and ask a question your flat memory got wrong because time mattered.

One store. A fixture that writes a fact, starts a new session, and retrieves that fact. A second fixture whose fact was superseded, which must return the new fact. If both pass, the memory loop is real.

### Summary: Agents and Multi-Step Workflows

An agent is a loop you can trace: plan, act, observe, stop, with a step cap and a human gate before any side effect. Ship that loop in one framework. [LangGraph](https://github.com/langchain-ai/langgraph) when you need checkpoints, the [OpenAI Agents SDK](https://github.com/openai/openai-agents-python) when you want a small runner and handoffs, [CrewAI](https://github.com/crewAIInc/crewAI) when a flow should wrap a crew, [Microsoft Agent Framework](https://github.com/microsoft/agent-framework) for new work that would have been AutoGen, [smolagents](https://github.com/huggingface/smolagents) when the action is code in a sandbox, and [Mastra](https://github.com/mastra-ai/mastra) when the app is TypeScript. Drive a browser with [Playwright](https://playwright.dev/) or [Stagehand](https://github.com/browserbase/stagehand) on one origin. Use [n8n](https://github.com/n8n-io/n8n), [Dify](https://github.com/langgenius/dify), [Flowise](https://github.com/FlowiseAI/Flowise), or [Langflow](https://github.com/langflow-ai/langflow) when the team needs a canvas, and test the run rather than the picture. Store decisions on purpose, keep working memory in the run, and start long-term memory with [Mem0](https://github.com/mem0ai/mem0), [Letta](https://github.com/letta-ai/letta), or [Graphiti](https://github.com/getzep/graphiti) only after a dated record would have done. Next is **Model Context Protocol (MCP)**, where those tools are a standard other clients can call, not a list hard-coded in one loop.

## Model Context Protocol (MCP)

The agent loop in the last chapter calls tools you registered in that one process. **Model Context Protocol (MCP)** is the wire format so a different client can call the same tools. Cursor, Claude, and Copilot can share one server. You stop rewriting the tool list every time you change editors.

MCP is not a new model and not a new agent framework. It is three things a server can offer: **tools** the model may call, **resources** the client can read, and **prompts** the client can fill in. Your smoke test is still one tool, one allowlist, and a result you can see in the client.

### What MCP is for

A tool call inside LangGraph or the OpenAI Agents SDK is a function in your process. The schema, the credentials, and the logs live next to that process. MCP lifts the tool across a transport. The client discovers the catalog, the model asks for a call, the client sends it to the server, and the server returns the result. The model still does not run the tool. The server does, which means the server's permissions are the blast radius.

Use MCP when two clients should see the same capability, or when the capability belongs to a system you do not want to import into the agent process. A retrieval function used only inside one Python script can stay a normal function. The day Cursor and a production agent both need it, that function becomes one MCP tool.

#### Tools, resources, and prompts as a standard

The [specification](https://modelcontextprotocol.io/) names three surfaces. Keep them separate so you do not hide a write inside something that sounds like a document.

- **Tools** are actions. A name, a description, a schema for the arguments, and a result. This is the same contract as function calling. The description is what the model uses to decide to call it, so write it like a skill description: when to use the tool, and what it will not do.
- **Resources** are data the client can read: a file, a row, a schema, addressed by a URI. Reading a resource is not the same as giving the model a tool that can list every file on the machine. Prefer a resource for something the user attached, and a tool for something the model may choose.
- **Prompts** are templates the client can offer, with arguments filled in before they reach the model. They are not a substitute for the prompt files you version in Git. Use an MCP prompt when a client should surface a reusable task ("summarize this ticket") without each user pasting it.

The current specification revision is **2026-07-28**. That revision makes the core a stateless request/response protocol, puts method and tool names in HTTP headers so a gateway can route on them, and gives list responses cache hints so a client can keep a tool catalog stable. The [announcement](https://blog.modelcontextprotocol.io/posts/2026-07-28/) is the short version. You do not need to re-implement the protocol. You need a current SDK, and you need to know that a server written a year ago may still be on the previous shape. The Tier 1 SDKs speak the new revision and still answer older clients.

Two transports cover the week. **stdio** is a process the client starts on your machine. The server inherits your user. **Streamable HTTP** is a server you reach over the network. A remote server without authentication is a tool catalog on the internet. Start on stdio.

#### Clients you already use: [Claude](https://docs.anthropic.com/en/docs/claude-code/mcp), [Cursor](https://cursor.com/docs/mcp), and [Copilot](https://docs.github.com/en/copilot)

You already picked one of these for a week in Coding Agents and Skills. Add MCP there before you write a server.

- **[Claude Code](https://docs.anthropic.com/en/docs/claude-code/mcp)** and the Claude desktop app attach servers in their MCP config. A local server is a command the client spawns. A remote server is a URL. Confirm the tool list in the client before you ask the model to use it.
- **[Cursor](https://cursor.com/docs/mcp)** reads MCP servers from the project or from your user settings. Project config belongs in the repo when the whole team should get the same server, and it must not contain a token. User config is where a personal key lives.
- **[GitHub Copilot](https://docs.github.com/en/copilot)** can use MCP servers in the editor and the CLI. Follow GitHub's own setup page for the config file name. The behavior you care about is the same: a catalog of tools, a call you can see, and a result that comes back into the chat.

The first connection is an official server, not yours. Point the [filesystem reference server](https://github.com/modelcontextprotocol/servers) at one directory you choose, ask a question that requires a file in that directory, and watch the client show the call. If the model answers without a call, the server is not connected or the question did not need the tool. Fix that before you write code. A client that silently skips a missing server will also silently skip the server you are about to publish.

### Run official and community servers

The [reference servers](https://github.com/modelcontextprotocol/servers) are the catalog: filesystem, git, fetch, and others people have published beside them. Treat a community server like a dependency that can run code as you. Read the tool list before you enable it. One server this week. A second server when the first call is boring.

#### The [MCP specification](https://github.com/modelcontextprotocol/specification) and reference servers

The **[specification](https://github.com/modelcontextprotocol/specification)** is the contract. The website [modelcontextprotocol.io](https://modelcontextprotocol.io/) renders the revision you should read. When a blog and the spec disagree, the spec revision wins. When an SDK and the spec disagree, check which revision the SDK README claims. As of the 2026-07-28 release, the TypeScript, Python, Go, and C# SDKs are the Tier 1 set that tracks the spec. Other languages exist at lower tiers. Pick Tier 1 unless you already live in another language and have checked that SDK's revision.

Run a reference server from the [servers repository](https://github.com/modelcontextprotocol/servers) with the narrowest scope the README allows. The filesystem server takes a directory. Give it a fixture folder, not your home directory. The fetch server can request URLs. Give it nothing until you have an allowlist of hosts. A "do anything" server is a shell with a protocol in front of it. Disable it.

After the client lists the tools, call one and read the raw result. Then ask for something outside the scope, such as a path you did not pass in. The server should refuse. If it returns the file, the scope is wrong. Fix the scope before you trust the client.

#### [Python SDK](https://github.com/modelcontextprotocol/python-sdk) and [TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk)

Use the official SDK for the language you already test. Both are on a **v2** line that implements the 2026-07-28 revision.

- **[Python](https://py.sdk.modelcontextprotocol.io/).** `pip install "mcp[cli]"` (or `uv add`). The high-level server class is `MCPServer`. A tool is a typed function and a docstring. v1 called that class `FastMCP`. If you are copying an old snippet, follow the [v2 migration notes](https://py.sdk.modelcontextprotocol.io/whats-new/) instead of fighting the import. The same process can serve stdio for a local client and Streamable HTTP for a remote one, and it still answers a client on the previous revision.
- **[TypeScript](https://github.com/modelcontextprotocol/typescript-sdk).** The v2 packages are `@modelcontextprotocol/server` and `@modelcontextprotocol/client`. Register a tool with a schema (Zod or another Standard Schema library) and a handler. The v1 package `@modelcontextprotocol/sdk` remains on the `v1.x` branch for fixes. New servers go to v2. Docs for the v1 API stay at [ts.sdk.modelcontextprotocol.io](https://ts.sdk.modelcontextprotocol.io/) so an existing server has a place to look during the move.

Hello-world tools that add two numbers prove the transport. They do not prove your server. The next section replaces that toy with one call your stack already makes.

### Write a small MCP server for your own stack

One internal capability. One tool. The capability should already have a function, a test, and an auth story. MCP is the adapter. It is not the place you invent the business logic.

A good first tool is read-only and narrow: "return the status of this ticket id," or "return the top chunks for this question" using the retrieval function you already score. A bad first tool is "query the database," "read a path," or "run this command."

#### Expose one internal API as tools

Wrap a function you can call from a unit test without a model.

1. **Name** the tool as a verb the model can choose: `get_ticket`, not `tool1`.
2. **Describe** when to call it and what it returns. Include the identifier the arguments require. If the description says "helps with tickets," the model will call it for every sentence that contains the word ticket.
3. **Schema** the arguments in the SDK's types. An id is a string with a pattern, or an integer, not a free-form "query" that accepts SQL.
4. **Call** your existing function. Map its errors to a tool error the client can show. Do not catch everything and return a cheerful string.
5. **Return** a small payload: the fields a later structured-output step might validate. Log the call on the server: tool name, argument ids, latency, and whether it was allowed. Do not log the full customer record if the record is the sensitive part.

Point the same client you used for the filesystem server at this process over stdio. Ask a question that includes a real fixture id. The trace should show `get_ticket` and the fixture's status. Ask a question with no id. The model should not invent an id, and the server should reject a malformed one. That pair of runs is the smoke test. Keep it next to the server the way the prompt smoke test sits next to the prompt file.

When a second client needs the tool, add the same server there. If the two clients disagree, the bug is in a client config, not a reason to fork the tool.

#### Auth, allowlists, and the blast radius of a tool

A tool is code that runs when a model is persuaded to ask. Persuasion is not a permission check. The server checks.

- **Allowlist the tools in the client.** Disable every tool you are not testing. A server that exposes twenty tools gives the model twenty actions on every turn. Turn on the one in the smoke test.
- **Allowlist the data.** A ticket tool accepts ids that exist in the fixture or in the caller's tenant. It does not accept "all tickets," and it does not follow an id from a document the model retrieved unless your policy says so. Retrieval text is untrusted, the same way user text is untrusted.
- **stdio inherits you.** Anyone who can start that process can use your files and your environment. Keep the command and the working directory in the client config explicit. Do not point a reference filesystem server at `~`.
- **HTTP needs an identity.** A Streamable HTTP server on a network uses the specification's authorization (OAuth, or the enterprise extension your gateway already has). Binding it to every interface with no token is how a demo becomes an incident. The 2026-07-28 headers (`Mcp-Method`, `Mcp-Name`) exist so a proxy can allow or deny a tool without reading the body. Use that if you already have a gateway. Do not invent a shared secret in the repo.
- **Writes wait.** A tool that creates, deletes, sends, or pays gets the human approval gate from the agent chapter. The MCP server can expose the tool and still refuse to run it until an approval id is present. The model's "the user said yes" in the argument is not the approval.
- **Secrets stay in the environment.** The server reads a key from the environment the process was given. The config you commit names the variable. It does not contain the value. Rotate the key if it ever landed in a chat or a screenshot, the same rule as the first API key.

The blast radius is the union of every tool you enabled, running as the user the server runs as, against the data those tools can reach. Write that sentence down next to the server. If you cannot finish the sentence, you enabled too much.

### Summary: Model Context Protocol (MCP)

MCP is how a tool, a resource, or a prompt becomes a catalog any client can call. Read the [specification](https://modelcontextprotocol.io/) at revision 2026-07-28, run one [reference server](https://github.com/modelcontextprotocol/servers) inside [Claude Code](https://docs.anthropic.com/en/docs/claude-code/mcp), [Cursor](https://cursor.com/docs/mcp), or [Copilot](https://docs.github.com/en/copilot), and confirm the client shows the call. Build your own server with the [Python SDK](https://github.com/modelcontextprotocol/python-sdk) or the [TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk) on the v2 line, and wrap one read-only function you already test. Allowlist the tool and the data, treat stdio as your user, and do not put a remote server on the network without authorization. A write tool waits for the same human gate as any other side effect. Next is **Harness engineering**, where the loop around the model — tools, sandbox, permissions, and retries — is the thing you design, whether or not you use MCP to plug the tools in.
